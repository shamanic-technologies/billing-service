# billing-service — repo conventions

## Tests need a local Postgres (not mocked) — start it before `pnpm test`

The suite hits a real Postgres: `tests/setup.ts` connects to `process.env.BILLING_SERVICE_DATABASE_URL || "postgresql://test:test@localhost/test"` and hand-builds the schema in `beforeAll`. With no DB running, EVERY suite that imports `src/db` fails with `AggregateError [ECONNREFUSED] ::1:5432` (looks like a code break — it is NOT). First-time setup on this machine:

```bash
brew services start postgresql@14
psql -d postgres -c "CREATE ROLE test LOGIN PASSWORD 'test' SUPERUSER"
createdb -O test test
```

Then `pnpm test` (vitest, `fileParallelism:false`, `maxWorkers:1`). Diagnose an ECONNREFUSED as "Postgres not running", never as a regression from the diff.

**The FIRST run against a fresh/cold DB fails the whole file with `Hook timed out in 10000ms` at `tests/setup.ts:17` and every test reported as SKIPPED — that is the setup building the schema, not a broken suite.** `beforeAll` hand-creates every table + index, which exceeds vitest's 10s default hook timeout on a cold local Postgres. The DDL is `IF NOT EXISTS`, so it committed anyway: **just re-run, and the second run is green.** The tell that it is this and not a real failure is the shape — 0 passed / 0 failed / N skipped plus a `Failed Suites 1` pointing at `setup.ts`, with no assertion anywhere. Do not "fix" it by raising `hookTimeout` or by trimming the setup. A fresh Conductor workspace also has no `node_modules` — `npx vitest` there dies with `Cannot find package 'vitest' imported from vitest.config.ts`, which means "install deps", not a config break.

**`tests/setup.ts` builds its schema with `CREATE TABLE IF NOT EXISTS`, so a change to an EXISTING table's shape never reaches a local test DB that already has it.** Adding a column (or moving a primary key) in `src/db/schema.ts` + the setup DDL leaves a machine that has run the suite before on the OLD table forever: every suite touching it dies with `PostgresError: column "<new_col>" does not exist` on a query the ORM built correctly, which reads exactly like a broken diff. Fix is one line — `psql -U test -h localhost -d test -c 'DROP TABLE IF EXISTS <table>;'` — then re-run and the setup rebuilds it in the new shape. CI is unaffected (fresh DB every run), so this only ever bites locally. Do NOT "fix" it by making the setup DDL conditional or by adding `ALTER TABLE`s to it. (Observed 2026-08-18 adding `feature_slug` to `brand_funnel_daily_budgets`: 44 failures across 4 files, all the same missing column.)

**Installing them takes ONE specific command here: `npx -y pnpm@9 install --frozen-lockfile`.** Both obvious paths fail and neither failure names its cause. Bare `pnpm install` runs corepack's pinned pnpm 11, which needs a newer Node than the v20 on this machine and dies with `TypeError [ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING]` out of `corepack/dist/lib/corepack.cjs` — nothing to do with this repo. `npm ci` refuses too: `package-lock.json` is stale (`Missing: decimal.js@10.6.0 from lock file`) because CI installs with pnpm and only `pnpm-lock.yaml` is maintained. Do NOT "fix" either by regenerating a lockfile — pin pnpm 9 for the install and leave both lockfiles alone. Then run the binaries directly (`./node_modules/.bin/vitest`, `./node_modules/.bin/tsc --noEmit`); `npx tsc` prints its own not-found banner that RTK reports as a false green.

**ONE `describe` per test FILE — a second `describe` in a file whose first one calls `closeDb()` in `afterAll` fails wholesale with `write CONNECTION_ENDED localhost:5432`.** `closeDb()` tears down the module-level postgres.js connection shared by every `describe` in that file, and vitest runs block 1's `afterAll` before block 2 starts. The symptom is a whole suite red on a connection error while the code under test is fine — indistinguishable at a glance from "Postgres not running". So when adding a feature-scoped block of tests to an existing suite, put it in its OWN file (vitest isolates modules per file, so each file gets a live connection) rather than appending a `describe` to a file that already closes the DB. Observed 2026-07-30: the daily-budget staff-notification tests were appended to `brand-daily-budget.test.ts` and all 12 failed on `CONNECTION_ENDED`; moving them verbatim to `brand-daily-budget-notification.test.ts` went green.

## Migrations are hand-authored AND hand-journaled — the journal is the apply-gate

This repo does NOT use `drizzle-kit generate`. `drizzle/meta/` snapshots stop at `0007`; every migration from `0008` onward is hand-written SQL, and `drizzle/meta/_journal.json` is maintained by hand. The boot migrator (`drizzle-orm/postgres-js/migrator` in `src/index.ts`, run before `app.listen()`) applies **only migrations listed in `_journal.json`** — a `drizzle/NNNN_*.sql` file with **no journal entry is silently skipped at boot and never runs in prod.**

When adding a migration:
1. Write `drizzle/NNNN_<name>.sql` (idempotent — `IF NOT EXISTS` / `ON CONFLICT` / single-row `UPDATE`).
2. Add a matching `_journal.json` entry with `when` **strictly greater than the previous entry's `when`** (the migrator gates on `when > last_applied.created_at`; the `idx`/filename number is cosmetic, drizzle reads by `tag`).
3. Verify against a throwaway COPY of the production database — never against production itself: run the real `migrate()` on the copy and confirm the row count / column change, plus that no unintended rows moved. Every database in the fleet now lives in one Postgres container on the box (`ssh` + `docker exec distribute-postgres-1 psql -U postgres -d billing_service`), so the copy is a scratch database you create there and restore prod into. (This used to be a Neon branch off production, taken in seconds; Neon is gone, so making the copy is now a step you perform, but it is still a step — a migration whose row-movement nobody checked is the thing this guards against.)

**Known live trap:** `0017_invite_promo_codes.sql` is unjournaled → it **never ran in prod**, so `invite_reward`/`invite_welcome` codes are absent and `POST /internal/credits/grant` throws `GrantPromoCodeMissingError` in prod (DIS-64 latent bug). Don't copy the "just drop a .sql file" pattern — always journal. (`0018` bumped the welcome gift to $25 and IS journaled.)

**A journaled + APPLIED seed is still not proof the row is in prod — query prod for the row itself, never infer it from `drizzle.__drizzle_migrations`.** Migrations are one-shot: once a tag is recorded as applied it never re-runs, so anything that later DELETEs or RENAMEs the seeded row leaves prod permanently without it while the migration ledger still says "applied". Observed 2026-07-30: `0023_first_load_match` was journaled AND present in `__drizzle_migrations` (id 34), yet prod had **no** `first_load_match` code row — the row 0023 inserted on 2026-06-17 had been hand-`UPDATE`d to `code='brand_welcome'`, `amount_cents` 0 -> 2500 (its `created_at` matched 0023's ship date exactly, as `admin_grant`'s matches 0025's). `grantFirstLoadMatch` therefore threw. **Note how the diagnosis nearly went wrong:** "the endpoint 500s in prod" was TRUE of the code and FALSE of reality — the endpoint had zero traffic (0 of 1255 `payment_intents` carried `metadata.billing_reason='initial_load'`), so nobody was ever charged-then-errored. Check traffic before assigning severity to a latent throw. Resolved by deleting the whole dead path (migration 0031), not by re-seeding: re-seeding would have restored a $25 grant that ignored the $25 entitlement. Consequence for design, not just for auditing: **any code path that depends on a seeded promo-code row must fail loud, and any user-visible commitment gated on one (a discount, a quoted amount) must be gated on the row actually existing** — that discipline is why the welcome-completion checkout discount used to check the seed existed before it would discount anything (that discount is now removed entirely — see "Checkout-page copy"). Prod check: `SELECT code, amount_cents FROM local_promo_codes ORDER BY code`.

**Parallel-branch collision (Conductor):** because both the filename number AND `when` are hand-picked, two branches developed in parallel routinely both claim the same next number (`0019`) with the **same `when`**. They merge cleanly as files (different tag = different filename) but the journal entries collide: each branch's boot already recorded its own migration at that `when`, so the OTHER migration fails the `when > max` gate and is **silently skipped forever** on that branch. Resolution at sync time: keep BOTH journal entries and give each a `when` **strictly greater than the highest already-applied** (e.g. `+86400000` apart). This forces a one-time **idempotent re-apply** of the already-applied one on its own branch — which is why migrations MUST be idempotent (step 1). Verify both tags appear in `_journal.json` with strictly increasing `when` before merging the sync PR. (Incident 2026-06-12: `0019_welcome_amount_200` (main, v0.28.3) vs `0019_credit_depletion_episodes` (staging, dunning) both at `when:1789725600000` → main→staging auto-sync PR #153 conflicted; resolved in #154.)

## Vocabulary (Stripe-aligned)

Naming follows Stripe Topups + Refunds APIs. When in doubt, search Stripe docs for the same term.

### Core money concepts

| Term | Definition | Source of truth |
|---|---|---|
| **credited** | Lifetime credits added to org (paid topups NET of money returned, + promos). | `SUM(succeeded payment_intents.(amount_received − amount_returned))` via stripe-service + `SUM(local_promos.amount_cents)` |
| **usage** | Platform AI cost consumed by org. Lifetime, all-time. | runs-service `GET /internal/org-usage-total` |
| **balance** | Funds usable right now for new work. `credited − usage`. **Use this for depletion/budget gates.** | computed at request time |
| **topup** | Auto/manual Stripe payment that increases credited. | stripe-service `payment_intents` (status='succeeded') |
| **gift / promo** | Non-payment credit (welcome bonus, promo redemption, manual adjustment). | `local_promos.amount_cents` |
| **returned** | Money given back on a topup — a succeeded **refund** or a **LOST dispute**. Deducted from credited. | stripe-service `amount_returned` on each PaymentIntent read |

### Refunds and lost disputes are netted out of `credited` (GH #290)

**Stripe never mutates a payment when money goes back out.** A fully refunded charge keeps `status: "succeeded"` at its full `amount_received` forever; the return lives on a separate Refund (or Dispute) object. So summing `amount_received` alone credits an org for money it was already given back — a manual dashboard refund used to leave the customer holding the full credit, on every refund and every lost dispute in the account.

stripe-service (#92, v0.27.0) mirrors Refunds + Disputes and exposes, on **every** PaymentIntent read surface, `amount_refunded` / `amount_disputed_lost` / `amount_returned`. `amount_returned` counts ONLY a `succeeded` refund and a `lost` dispute — a pending refund, a refund that later failed/was canceled, and an open or won dispute are all excluded, so partial refunds and reverted refunds are correct by construction.

Billing nets it in ONE place: `netReceivedCents(pi)` in `src/lib/stripe-service-client.ts`, used by BOTH `sumSucceededTopupsForCustomer` (real-user `/v1/accounts` path) and `sumSucceededTopupsForOrg` (user-less `computeBalance` path). Same arithmetic on the same rows, so the two surfaces can never disagree about how much an org paid in. **Never re-add a bare `amount_received` sum** — and note the netting also (correctly) shrinks `paidTopupsCents`, which drives the postpaid tier ladder: a refunded payment must not keep growing the org's credit line.

Fail-loud: a PaymentIntent arriving without `amount_returned` (stripe-service older than #92) **throws**. Defaulting it to 0 would silently resurrect the bug. Consequence: billing must not run against a stripe-service below v0.27.0.

**⚠️ Automating a correction that was previously done BY HAND double-counts unless you delete the manual rows first.** Before this shipped, the only way to take back a refunded top-up was a NEGATIVE `local_promos` row inserted by staff. Those rows survive the automation, so the org gets debited twice — once by the manual row, once by the netting. Cost 2026-07-29: org `17d240d8-…` carried a `-5000` `admin_grant` row ("Refund offset: $50 erroneous auto-topup") from 21 July; after the netting shipped its credits read $103.50 instead of $153.50 and its balance went to −$41.98 instead of +$8.02, which would then have triggered a month-end sweep charge. Kevin caught it from the dashboard, not from any test. The row was deleted; it was the only one.

So whenever you automate something staff used to patch manually, sweep for the manual patches in the SAME ship: `SELECT * FROM local_promos WHERE amount_cents::numeric < 0` (a negative grant is almost always a hand-rolled correction, since promos are credits) and grep the descriptions for the concept you just automated. A rendered `Bonus credit +$-50.00` in the dashboard Gifts list is the visible tell that one is still there.

**⚠️ The netting is only as good as stripe-service's refund MIRROR — and the mirror does not see every payment rail.** `netReceivedCents(pi)` subtracts `amount_returned`, which stripe-service computes as a live query over its `refunds` + `disputes` silver tables. A refund that never lands in those tables is invisible here: the money is off our Stripe balance, and billing still counts it as `credited`. Nothing fails, nothing logs — the org simply keeps spendable credit it no longer has.

Prod, 2026-07-31: four partial refunds issued in the same minute. The two on **card** payments mirrored and netted correctly (one org landed at a balance of 0.09 cents, exactly as intended). The two on **Link** payments did not, and those orgs still read +$40.39 and +$39.31. Stripe uses `re_…` for a refund of a charge and **`pyr_…`** for a refund of a payment (Link and other non-card rails); stripe-service's event router keyed on the id prefix and had no `pyr_` branch, so those events were stored and dropped. Filed as stripe-service#100.

Consequence for us, beyond the arithmetic: **do NOT paper over an unmirrored refund with a compensating negative `local_promos` row.** That is precisely the hand-patch the section above warns about — the moment the producer fixes its mirror and back-fills, the netting lands too and the org is debited twice. The correct move is to fix or await the mirror. If you need to know whether a refund is actually visible to billing, check that it exists in stripe-service's `refunds` table, not that it succeeded in the Stripe dashboard.

**The platform-wide surface is netted too** (stripe-service #95, v0.28.0): `GET /public/stats/billing` reads `total_net_cents` (and per-bucket `net_cents`) for `total_credited_cents` AND `total_revenue_cents`, so the platform total equals the sum of the per-org ones. `total_paid_cents` keeps its original GROSS meaning and `total_returned_cents` is exposed alongside. Revenue is net on purpose: it feeds the landing investor-metrics page, and money we refunded is not revenue we earned.

### Stripe `customer.balance` is NOT used — but Stripe still APPLIES it to every invoice, so it must stay at 0

Pre-#104, billing-service wrote `usage_applied` CBTs to Stripe via `customers.createBalanceTransaction`. Those debits contaminated `customer.balance` (it no longer represented pure prepaid credit). Post-#0016 stripe-service v0.16.3 dropped `customer.balance` from its API surface entirely. Billing-service must **never read `customer.balance`** — derive `credited` from `payment_intents.amount_received` (real money paid) plus local promo grants.

**"We don't read it" is NOT the same as "it can't hurt us." Stripe applies the customer credit balance to every invoice at finalization, automatically, with no opt-out flag.** So the moment billing moved auto-topup reloads from a bare PaymentIntent to a finalized Invoice (#276, `reloadViaInvoice`), every stale CBT from the pre-#104 era became live again — silently, on a path that had been dormant for months. On **2026-07-31** the month-end sweep raised a **$500** invoice for org `b645207b-…`; Stripe added that customer's `starting_balance: 198599` and charged **$2,485.99**, which the card declined for insufficient funds. Nothing in billing's code or tests could see it: the line item was correct, and the whole distortion lived in a Stripe-side field billing deliberately ignores.

The audit at the time found **13** customers with a non-zero balance, all pre-#104 residue: one at **+$1,985.99** (legacy `usage_applied` debits) and twelve between **−$1.82 and −$13.40**, mostly ≈ −$2.00 — the old welcome grant written as a Stripe credit. Every one of those negatives was a **double-credit waiting to fire**: billing already counts that welcome grant in `local_promos`, so the customer's first invoice would have discounted it a second time. All 13 were zeroed with compensating CBTs.

**Invariant: `customer.balance` must be 0 for every customer, forever.** Nothing in the fleet writes it today, so the only ways it comes back are a manual Stripe-dashboard adjustment or a resurrected legacy path. Check it whenever an invoice total disagrees with the amount billing asked for — the tell is `starting_balance != 0` on the Stripe Invoice, and `amount_due != subtotal`. Do NOT "fix" a distorted invoice by adjusting the line item; zero the customer balance. (Follow-up filed on stripe-service: assert `customer.balance == 0` in the off-session invoice endpoint and fail loud, so this can never again reach a customer's card.)

## BYOK (Bring Your Own Key) cost source

`runs_costs.cost_source` ∈ `'platform' | 'org'`. ONLY `platform` rows are billed.

| `cost_source` | Who paid AI provider | We bill the org? |
|---|---|---|
| `platform` | Distribute (our API key) | **Yes** — counted in usage from runs-service |
| `org` | The org (their own API key) | **No** — tracking only, never deducted |

When reconciling or computing real cost: `WHERE rc.status='actual' AND rc.cost_source='platform'`. Including `org` rows would over-state.

## Local promos (`local_promos` table)

The only persistent ledger billing-service owns. One row per (org, promo_code) — `UNIQUE (org_id, promo_code_id)`. Welcome trial = `code='welcome'` ($5 grant; seeded @$2 by migration 0016, bumped to $25 by 0018, reverted to $2 by 0019, set to $5 by 0028). Welcome-completion gift = `code='welcome_completion'` (technical code seeded at 0; dynamic per-row amount — see "Welcome-completion gift"). Other codes are admin-managed.

**Removed — do NOT reintroduce `first_load_match` (migration 0031).** It backed `POST /v1/accounts/wallet_setup` (dollar-for-dollar match on the first paid load, capped $25). The whole path was dead: onboarding migrated off it (the dashboard's own `onboarding-flow.test.ts` asserts the flow does not contain `wallet_setup`, and its leftover `walletSetup()` helper had zero call sites) and prod never completed one — **0 of 1255** `payment_intents` carried `metadata.billing_reason='initial_load'`. Worse, it capped at $25 **on its own** with no reference to the free-credit entitlement, so `welcome` + `first_load_match` granted **$30** of free credit against a $25 entitlement — it contradicts the rule 0029 established. Its promise ("$25 free once you put money in") is now served by `welcome_completion`, on the checkout path onboarding actually uses. A removal guard in `tests/integration/accounts.test.ts` ("removed surfaces") asserts the route 404s and no `first_load_match` code row exists.

**Re-pricing a promo code at runtime (NO migration):** `PATCH /internal/promo-codes/:code` body `{ amountCents }` updates `local_promo_codes.amount_cents` in place (`GET /internal/promo-codes/:code` reads it). This is the live source read at redeem time, so it changes what NEW signups receive immediately — use this to re-price the welcome gift, not a migration. Service-auth only; the gateway must gate it to staff. Migrations are now only for the SEED DEFAULT (a fresh prod DB) — a `WELCOME_PROMO_AMOUNT_CENTS` change still wants a migration so the default is right on the next deploy, but day-to-day amount tweaks go through the endpoint.

**Changing the welcome SEED DEFAULT (migration path) = 4 sites in lockstep (tests do NOT run drizzle migrations — they hand-build schema + seed in `tests/setup.ts`):** (1) `drizzle/NNNN_*.sql` migration row + journal entry, (2) `WELCOME_PROMO_AMOUNT_CENTS` in `src/db/schema.ts` + its comment, (3) the `local_promo_codes` welcome seed in `tests/setup.ts`, (4) the welcome-amount assertions + comments across the WHOLE integration suite — NOT just `{promo,accounts}.test.ts`. As of v0.49.1 the welcome amount is asserted (directly or via a derived total) in `tests/integration/{promo,accounts,promo-codes,public-stats,admin-grants,credits-grant,internal-account-teardown}.test.ts`. Do NOT trust a mental list of files — `git grep -n "welcome" tests/` and cross-check every bare `200`/`$2` (assertions pass values positionally, e.g. a `welcome + promo = TOTAL` derived sum, an `insertTestPromoGrant({ amountCents: 200, promoCode: "welcome" })` fixture, or an `invite_welcome/invite_reward` doc comment). Miss (3)/(4) and the suite goes red (or worse, silently asserts the old amount). The `INVITE_GRANT_AMOUNT_CENTS` / `invite_welcome` / `invite_reward` grant AMOUNT is independent — leave it at 2500 — but its test COMMENTS reference the welcome row's dollar figure ("replaces the $X welcome row", "$X + $25 = $Y"), so those strings + any additive T6-style total DO move with the welcome amount.

Referral-promise grants use `code='referral_reward'` (migration 0033) and are the second STACKING kind alongside `admin_grant`: they carry `idempotency_key = promise:<promise_id>`, which exempts them from the `(org, promo_code)` uniqueness so one inviter can hold several. Its `amount_cents` is **not** a placeholder — it is the live figure a NEW referral promise freezes ($500). See "Free-credit promises".

`amount_cents` is positive (these are credits). `numeric(16,10)` — Drizzle returns it as a JS string. Use Decimal.js (via `src/lib/cents.ts` helpers) for arithmetic; never cast to Number for math.

## Free-credit promises — an org carries SEVERAL at once (`src/lib/free-credit-promises.ts`, migration 0033)

A **promise** is an amount of free credit an org will receive once its cumulative SUCCEEDED payments (net of refunds and lost disputes — the same figure the welcome completion uses) reach a **bar**. One row per promise in `free_credit_promises`.

Until 0033 an org had exactly ONE outstanding promise, expressed as the two `billing_accounts.free_credit_*` columns. The referral offer breaks that shape: an inviter who converts ten referrals carries ten promises at once, each worth a different amount, each earned at a different bar, and each of them created because somebody ELSE paid. A single pair of numbers on the account cannot express that.

**The rules (product-locked):**

- `amount_cents` and `paid_trigger_cents` are **FROZEN at creation and never updated**. Re-pricing an offer later reaches only promises created after the re-price — no cutoff date, no backfill, every existing customer grandfathered by construction. Same discipline as 0032, and the reason `insertStackedPromise` is the ONLY writer.
- **The bar of a NEW promise is `(highest bar this org already carries) + (its own amount)`** — whether or not that earlier promise has been earned, because cumulative payments only ever go up. `highestBarCents` reads BOTH the promises table and the account's own frozen trigger, so it is right even for an org whose welcome promise row was never materialised. The ladder:

  | situation | ladder |
  |---|---|
  | brand-new $400 account | $400 @ $400 (unchanged from today) |
  | ...then referred | + $500 @ $900 |
  | ...a third promise | + $500 @ $1,400, and so on, no ceiling |
  | grandfathered $25 account, referred | $25 @ $25, then $500 @ $525 |

- **An outstanding promise is a promise, not money.** No `local_promos` row exists until it is granted, so it is absent from `credited` / `balance` / `actual_balance` / spendable everywhere. Do NOT "helpfully" surface it in a balance figure.
- **The referral offer has NO up-front portion** — the whole amount lands when the bar is crossed. The $5 up-front gift belongs to the welcome offer only, and is unchanged for every cohort.
- **Referral credits STACK with the welcome offer, never replace it.** Two consequences that are easy to get backwards: (a) the welcome remainder subtracts `sumEntitlementGrantsForOrg` (everything EXCEPT `referral_reward`) — counting a $500 referral there would silently cancel a $400 welcome remainder; (b) `grantCredit('invite_welcome')` no longer DELETES the org's `welcome` row (it used to, so the two could not stack). **Nothing on an invite / referral path may remove or reduce an existing promise or an already-granted credit.**

### The referral chain

1. Someone signs up through another org's invite link. client-service calls **`POST /internal/referrals/claim`** `{orgId, referrerOrgId}`; the INVITEE gets an outstanding promise carrying `referrer_org_id`, and nothing is granted.
2. When the INVITEE **EARNS** it (their OWN payments cross their bar), that same moment opens an identical promise for the INVITER, carrying `referred_org_id` = the invitee, at the INVITER's own next bar.
3. The inviter earns it only on their OWN payments. **It is never granted for free, and it is never opened by the invitee merely signing up.** Repeats without limit.

**The referral amount lives on the `referral_reward` `local_promo_codes` row ($500 today)** — NOT a code constant and NOT a column default. That row is already re-priceable at runtime via `PATCH /internal/promo-codes/referral_reward`, so re-pricing the referral offer needs no migration and cannot reach a promise that already froze its own figure. Unlike `admin_grant` / `welcome_completion`, its `amount_cents` is therefore **not** a 0 placeholder. The INVITER's promise copies the INVITEE's frozen amount (literally "identical"), not the current price.

**Exactly-once is structural — no new bookkeeping:**

- the grant is a `local_promos` row with `idempotency_key = promise:<id>`, deduped by `idx_local_promos_org_idempotency`. It uses the STACKING key (like `admin_grant`) rather than `(org, promo_code)`, because an inviter legitimately holds several referral grants under one code.
- the inviter promise is deduped by the partial unique index on `(org_id, referred_org_id)`.
- a re-claimed invite hits the partial unique index on `org_id WHERE referrer_org_id IS NOT NULL` and is a no-op; a claim by a DIFFERENT inviter is a **409** (an org is referred once — guessing which inviter wins is not billing's call).

**Deadlock + crash safety.** The invitee's grant + stamp commit in one transaction; the inviter's promise is opened in a **SEPARATE** transaction afterwards — never nested, because A referring B while B refers A would otherwise deadlock on each other's `billing_accounts` row lock. If the process dies in between, `reconcileInviterPromises` re-opens it on the next settle, and the sweep keeps that org in its candidate set until the inviter promise exists.

**Who drives it (never the browser).** `settleFreeCreditPromises` (`src/lib/free-credit-settlement.ts`) is the ONE entry point — it materialises the welcome promise, runs `settleWelcomeCompletion`, then `settleReferralPromises`. Called from `composeAccountFunds`, the checkout route, `GET /v1/free-credit-promises`, and unconditionally from the hourly sweep. A request can only make an already-EARNED grant land sooner; every condition is derived from Stripe's record of money received plus billing's own ledger. `computeBalance` still deliberately does NOT settle.

**Fail loud:** a missing `referral_reward` seed THROWS (→ 500 on the claim, 502 on the account read), exactly like the `welcome_completion` seed. Prod HAS lost promo-code seeds before (see the migrations section).

**The sidebar headline: `outstanding_total_cents`.** An org routinely holds several promises at once (the welcome remainder plus one per converting referral), and the sidebar states the TOTAL still coming. The dashboard is forbidden from summing money in the browser — a displayed money figure arrives ready from the service that owns it, or two surfaces end up disagreeing about one number — so `GET /v1/free-credit-promises` answers it. `sumOutstandingPromiseAmounts` adds up the very rows the same response returns, never a second query, so the headline and the list cannot state different figures and it inherits every rule those rows obey (welcome remainder net of what was already gifted, a promise worth nothing dropped, a granted promise gone). Nothing outstanding → a canonical `"0.0000000000"`, never null and never an absent field. ADDITIVE: `promises[]` and every per-promise figure are byte-unchanged, so a consumer that does not know about it keeps working. **It is not money the org can spend** — it enters neither `credited`, `balance` nor spendable, which is the same separation that stops the billing page double-counting a promise.

**The welcome promise row is a MIRROR, not the source of truth for the welcome grant.** `settleWelcomeCompletion` still reads `billing_accounts.free_credit_*` and its arithmetic is untouched; `ensureWelcomePromise` copies those frozen figures into a row so the welcome offer is one of the listed promises and so a referral bar can stack above it. It is deliberately NOT created for an account excluded from the welcome completion (that promise can never be granted, so listing it would be a lie), which is also why the sweep's candidate query skips a `welcome` promise whose account is ineligible.

Verified on a prod fork: 89/89 eligible accounts backfilled at their own grandfathered **2500/2500**, 0 granted, promo rows + gifted total untouched, re-apply touches **0** rows.

**Teardown** deletes an org's OWN promises. A promise held by ANOTHER org that merely REFERENCES it (an inviter's promise naming the deleted org as the referral that converted) is deliberately left alone — the inviter genuinely earned it.

### Naming the referral (`src/lib/brand-service-client.ts`)

`referred_org_id` is a UUID, and the dashboard cannot turn it into anything a person reads: every brand read reachable from the customer dashboard is scoped to the CALLING org (`GET /v1/brands` lists the caller's own), and there is no by-org lookup for a foreign org anywhere on the gateway. An inviter holding three pending $500s would see three identical rows. So billing resolves it: `GET /v1/free-credit-promises` also carries **`referred_org_name`** + **`referred_org_domain`** (the dashboard renders the logo from the domain via logo.dev).

**billing is the only service that can make this call.** It is the only one that knows the referral relationship exists, and that relationship is exactly what authorizes revealing anything about the other org at all — the inviter shared their link with that person, and a referral program that cannot name who converted does not work. No other service can make that authorization decision, so no other service can safely perform the lookup.

- **Not a general org-lookup capability.** `resolveOrgDisplayIdentity(orgId)` is called from ONE place, for the org named on a promise this org holds, and returns a name + a domain. Nothing about that org's spend, campaigns, credits or performance — the inviter is entitled to know WHO converted, not to see their business. Do not widen it.
- **Reads `GET /orgs/brands` on brand-service with `x-api-key` + `x-org-id` only** (brand-service `apiKeyAuth` + `requireOrgId`). Service-auth, org-keyed, one org: no fake `x-user-id` sentinel is invented, and the fleet-wide `/internal/brands/all` is deliberately NOT used. Picks the org's oldest brand carrying a domain (its founding brand), so the row does not rename itself as they add more; falls back to the oldest overall so a no-website org still gets its name.
- **Fail-soft, and this is the documented exception to fail-loud.** The promise itself is the money-bearing information: a lookup that fails (brand-service down, unconfigured, the org has no brand) logs loudly and yields **null**, and the promise is still returned with its amounts intact. Never a value fabricated from the UUID — a placeholder name is worse than no name, so a nameless org simply renders without one.
- **The fields are ADDITIVE and optional.** The dashboard reader (distribute.you `FreeCreditPromiseSchema`) shipped them `.nullable().optional()` ahead of this, so the contract is `referred_org_name` / `referred_org_domain` byte-equal — conform to it, do not rename. Absent entirely on a promise with no referred org.
- **`referrer_org_id` is deliberately NOT resolved.** The invitee reached us through that org's own invite link, so they already know who it was; they hold exactly one referral promise (nothing to disambiguate); and no consumer reads it. Revealing less is the default.
- Needs `BRAND_SERVICE_URL` + `BRAND_SERVICE_API_KEY`, in every environment that runs this service. They live in the service's env file on the box (`/root/distribute/env/billing-service.env`); the Railway `${{shared.*}}` reference they used to be is gone, so a value shared across services is now shared by being written into each service's file.

### Telling the two sides (`src/lib/referral-notifications.ts`, migration 0034)

The money worked end to end before this and nobody was ever told. A referrer has no reason to open the dashboard on the day someone they invited converts, so they could bring in three converting customers and never learn the referral worked. billing is the service that opens the promises and grants them, so it is the only place that can observe those moments.

**TWO messages, and the list of what was dropped is the design:**

| eventType | to | when |
|---|---|---|
| `referral-reward-opened` | the REFERRER | someone they invited converted, so a reward opened at their own next bar |
| `referral-credits-granted` | whoever earned it, either side | the credits actually landed |

Not sent, deliberately: **the invitee's promise being CREATED at signup** (nothing is earned yet, and they are mid-onboarding reading the same thing on screen); **"opened" when the reward is already earned as it opens** (see below); and anything about the welcome offer, which is the other promise kind.

**The collapse rule is the whole reason `alreadyEarned` exists.** An inviter's new bar is `(their highest bar) + $500`, which says nothing about what they have already paid — so a referrer already past that bar earns the reward on the very next settle. Sending "$500 is on its way" and then, minutes later, "$500 arrived" teaches nothing with the second message. `notifyReferralRewardOpened` therefore reads that org's paid topups once, and stays silent when the bar is already met; the granted message carries the whole story and names the same referral. That read **fails OPEN** (a throw means "not yet earned", so the referrer is still told) — a possible duplicate beats silence about money.

**Exactly-once is its own state, because "did we grant" and "did we tell them" are different questions.** The grant's idempotency cannot answer the second: the hourly sweep re-examines every outstanding promise on every tick, so with no marker a customer would be mailed about the same event forever. Migration 0034 adds `opened_notified_at` / `granted_notified_at` to `free_credit_promises`, each claimed by a conditional `UPDATE … WHERE <marker> IS NULL RETURNING` — only the caller whose update returns a row sends, so two racing settles produce one email. **The claim is taken AFTER the recipient resolves**, so a cold stripe-service leaves the marker NULL and the next tick retries instead of burning the only send; an org whose billing customer exists with no address IS marked, because there is nothing to retry against. 0034 also backfills every pre-existing promise as already-notified, so the first sweep after the deploy cannot mail anyone about days-old activity. (Measured on prod at ship time: 89 welcome rows, **zero** referral rows, so the backfill was belt-and-braces.)

**⚠️ Every `sendEmail` needs an `x-run-id` naming a run that ALREADY EXISTS in runs-service — a minted UUID silently drops the mail.** transactional-email-service records each send as a run CHILD of the id you hand it, so runs-service answers `400 parentRunId <uuid> does not exist` and the email service returns **200** with `{sent: false, reason: "Run creation failed: …"}`. Every send in this repo is fire-and-forget, so nothing surfaces it: no throw, no 5xx, no log on our side. Verified against prod both ways — a random uuid gives `sent: false`, a real platform run gives `sent: true`, and the zero sentinel (`00000000-…`) fails like any other non-existent run. Omitting the header entirely is a `400 Missing required headers`.

So a send with **no end user behind it** (a sweep, a settle, a scheduler tick) must open a platform run first: `createPlatformRun(taskName)` in `src/lib/runs-client.ts` (`POST /v1/platform-runs`, `x-api-key` + `x-service-name`, no org/user/parent), then `completePlatformRun(id)` afterwards — the create IGNORES any `status` in its body and always stores `running`, so without the PATCH these pile up open forever. The run declares **no cost**: billing spends nothing to ask another service to send an email, and the email service declares its own. A run that cannot be opened is treated exactly like an unresolvable recipient — skip WITHOUT claiming the marker, so the next tick retries.

The same trap bit the **dunning follow-ups**, which used `ep.runId ?? crypto.randomUUID()`: an episode opened by an authorize that carried no valid `x-run-id` would have had its +3d/+10d mail dropped in silence. That fallback is now `createPlatformRun("dunning-followup")`. **Never write `runId: crypto.randomUUID()` into a `sendEmail` call.**

**Fail-soft, the documented exception to fail-loud, same posture as the identity lookup above.** Every path logs loudly and returns; nothing here can fail, delay or roll back a grant, and the grant transaction has already committed before any of it runs. A notification failure must never touch the money it describes.

**Recipient = the org's Stripe billing email** (`fetchOrgCustomer`, the user-less org-keyed read), passed as `recipientEmail` — transactional-email-service accepts it in place of an `x-user-id` lookup, so no fake user identity is invented on a settle. Both messages name the referral through the same `resolveOrgDisplayIdentity` the Billing page uses, under the same authorization, and never fabricate anything from the UUID: an unresolvable org renders as "A new customer" in the opened message and drops out of the granted message's `{{reason}}` sentence.

**Both templates are registered by THIS service** (`src/instrument.ts`), since the fleet convention is that a template belongs to whoever SENDS it. Every `{{variable}}` in them is always supplied and never empty — an unset one renders as a literal `{{placeholder}}` in a customer's inbox, which is why `referredOrg` carries a phrase rather than a possibly-null name and why `reason` is composed in code rather than branched in the template. A test pins the template's variable set against the sender's.

## Welcome-completion gift — "$N in free credits", automatic (`src/lib/welcome-completion.ts`)

Onboarding promises every new customer **$N of free credits**. Signup only grants the `welcome` row ($5 today), so for months the remainder was granted BY HAND (staff `admin_grant` rows described "Welcome credits (2/2)"). `welcome_completion` (migration 0029) automates the remainder.

**The rule (product-locked):**

- An org receives **its own `free_credit_entitlement_cents` in free credits IN TOTAL**, welcome gift included.
- The completion amount is **DERIVED**: `entitlement − SUM(local_promos EXCLUDING referral rewards)` (`sumEntitlementGrantsForOrg`). **Never hardcode the difference** — it stays correct across cohorts, if the welcome amount is re-priced (0018/0019/0028 all moved it), or if the org never got a welcome row at all. A re-priced $10 welcome leaves a $15 completion on a $25 account; an org already gifted its full entitlement gets nothing.
- It is **EARNED when cumulative SUCCEEDED payments reach that account's own `free_credit_paid_trigger_cents`**, net of refunds + lost disputes. The trigger is **money actually received, NOT usage consumed** — the account model is threshold-postpaid, so an org can consume on credit before paying anything, and we must not gift credits to someone whose card may still fail.

### The offer amount is a PER-ACCOUNT property, frozen at account creation (migration 0032)

Both figures used to be module-level constants, so re-pricing the offer re-priced it for **every existing customer at once**. They now live on `billing_accounts` — `free_credit_entitlement_cents` + `free_credit_paid_trigger_cents`, `integer NOT NULL` — written ONCE from the **column DEFAULT** at INSERT (`findOrCreateAccount` inserts `org_id` only) and never updated afterwards.

- **Two cohorts today.** Accounts predating 0032 carry **$25 / $25** (`GRANDFATHERED_FREE_CREDIT_*`); accounts created after it carry **$400 / $400** (`CURRENT_FREE_CREDIT_*`). Verified on a prod fork: **93/93** existing accounts landed at 2500/2500 and a fresh `INSERT … (org_id)` came back 40000/40000.
- **Read the ROW, never a constant.** There is deliberately no bare `FREE_CREDIT_ENTITLEMENT_CENTS` export any more — a global entitlement is the exact bug this shape removes. `CURRENT_*` is the DB default, `GRANDFATHERED_*` is documentation for the cohort that must keep reading $25 forever. Do not re-price `GRANDFATHERED_*`.
- **A future re-price is one line**: move the column DEFAULT. Existing rows already hold their value, so every customer grandfathers automatically — **no cutoff date, no backfill, no new rule to stack**. (Contrast `WELCOME_COMPLETION_LAUNCH_AT_ISO`, which needs a date because it is a claim about payment HISTORY. This is a claim about the account itself, so the row carries it.)
- **Migration 0032's statement ORDER is the whole trick**, and it is why re-applying is safe: `ADD COLUMN … DEFAULT 2500` backfills existing rows with the offer they signed up under, *then* `ALTER COLUMN … SET DEFAULT 40000` aims future signups at the new one. On a re-apply, `ADD COLUMN IF NOT EXISTS` is a no-op, so a $400 account can never be re-stamped to $25. A test in `tests/integration/free-credit-offer-cohorts.test.ts` replays those exact statements and asserts it.
- **The $5 up-front `welcome` gift is unchanged for BOTH cohorts.** Only the total and the trigger differ.
- **`insertTestAccount` defaults to the GRANDFATHERED $25/$25**, so every suite written before the re-price keeps exercising the offer it was written against (same rationale as the `welcomeCompletionEligible: false` default). Pass `freeCreditEntitlementCents`/`freeCreditPaidTriggerCents` for the new cohort; to exercise what a REAL signup gets, insert with no offer columns at all so the DB DEFAULT applies.

**Who drives it (never the browser).** Nothing pushes into billing when a Checkout payment lands (stripe-service only mirrors the PaymentIntent), so `settleWelcomeCompletion(orgId, paidTopupsCents, fetchPaidTopupsBeforeLaunchCents)` is called from every path that ALREADY holds the org's paid-topups sum — `composeAccountFunds` (so the dashboard read right after a payment makes it land in seconds) and the checkout route — plus, unconditionally, the hourly `runWelcomeCompletionSweep` on the existing dunning scheduler. A request can only make an already-EARNED grant land sooner; the condition is derived entirely from Stripe's record of money received plus billing's own ledger, so nothing a caller asserts can conjure a grant. `computeBalance` deliberately does NOT settle — `GET /internal/campaigns/:id/affordability` is documented side-effect-free and authorize stays hot-path-thin.

**Idempotency** is the existing partial unique index `idx_local_promos_org_promo … WHERE idempotency_key IS NULL` — no new state. Concurrent settles race the INSERT; losers read `already_granted`.

**NO BACKFILL means exactly one thing: do not retroactively credit an org whose payments had ALREADY crossed its trigger before the automation launched.** It does NOT mean "every org that existed at ship time is ineligible forever" — that is how migration 0029 first implemented it, and it is far too wide. Measured against prod: of the 88 accounts 0029 demoted, only **10** had actually crossed $25; **78** were excluded wrongly and **67** of those are still gifted under $25 in total. Those 67 are precisely the population the automation exists for (signed up long ago, hold the $5 welcome row, have not paid $25 yet) and the founder was hand-granting each one, so the over-broad predicate meant the feature removed none of the work it was built to remove. Migration **0030** gives every pre-existing account its eligibility back.

The genuine exclusion is decided per org, at settle time, against `WELCOME_COMPLETION_LAUNCH_AT_ISO` (`2026-07-30T00:00:00Z` — a literal, never `now()`):

- billing does not store cumulative payments, it READS them — and it does not DERIVE the as-of-launch figure either. `sumPaidTopupsForOrgAsOf(orgId, WELCOME_COMPLETION_LAUNCH_AT_UNIX)` asks stripe-service directly (`GET /internal/payment_summary/by-org/{orgId}?as_of=`, v0.33.0), summing `amount_net` across every currency with activity. `settleWelcomeCompletion` makes that call ITSELF, lazily, inside the one branch that needs it: there is no callback parameter and no caller-supplied figure, so the account read, the checkout route, the promises read and the hourly sweep cannot disagree about a money verdict, and none can skip the check. **Never reintroduce a client-side filter over the org's PaymentIntents** — per-object date filtering was the last piece of vendor-shape knowledge on the money path, and it is gone (`sumSucceededTopupsFor{Customer,Org}Before`, the `createdBefore` helper and the `created` field on `StripePaymentIntent` were all deleted with it).
- **BOTH sides of the subtraction are bounded — payments AND returns Stripe created strictly before the instant.** This is a deliberate semantic CORRECTION, not a port. Billing used to bound the payment and subtract EVERY return ever, so an org that paid $200 before launch (excluded) and was refunded $150 today read as $50 pre-launch and the sweep handed it a welcome gift a year later, because of a refund that happened long after the launch it is measured against. A verdict about a past instant must not be rewritten by later events, or it is not a grandfather but a rolling re-computation that wobbles for as long as the org stays a sweep candidate. Some orgs' verdicts changed with this ship, in the direction of STAYING excluded.
- **The echoed `as_of` is checked and a mismatch THROWS.** A stripe-service older than v0.33.0 ignores the bound and answers the ALL-TIME figure; the two replies are otherwise identical, so taking it silently would grandfather orgs out of a gift they are owed. Billing must not run against a stripe-service below v0.33.0.
- the check sits AFTER the trigger and entitlement guards, so it is only ever reached by a pre-launch org that has since crossed $25 and still has entitlement left — and that org's outcome is terminal either way (excluded, or granted and then permanently entitlement-full). **One extra read per org, ever.** A post-launch account skips it entirely (`created_at >= launch`): it has no pre-launch payments by construction, so it can never be demoted.
- the answer is then FROZEN onto `welcome_completion_eligible = false`, which is now that column's ONLY meaning ("crossed the trigger before launch"). Freezing is safe because the input is immutable history — re-deriving can only return the same thing — and it keeps the excluded orgs out of the sweep's candidate set for good.

Verified on a prod fork: 88/88 eligible after 0030 (was 0/88), grant rows + gifted total untouched, re-apply touches **0** rows. 0030 only ever sets `true`, so it cannot demote anything; re-applying it after a resolution merely re-promotes one of the 10, whose next settle re-derives the identical answer from the same pre-launch payments. No grant can slip through in between, because the check precedes the INSERT inside the same call.

**`insertTestAccount` still defaults `welcomeCompletionEligible: false`** (an already-excluded org) so paid-topup mocks in unrelated suites never trip the grant and shift their credited totals. Pass `true` to exercise the gift, plus `createdAt: <pre-launch date>` to stand in for one of the pre-existing orgs.

**Fail loud:** a missing `welcome_completion` seed THROWS (→ 502 on the account read). Swallowing it would leave a buyer short of credit they were promised, which is the exact failure this exists to remove. This is not paranoia — prod HAS lost promo-code seeds (`invite_reward`/`invite_welcome` never applied per 0017; `first_load_match` was seeded by journaled 0023 yet is absent from prod today, apparently hand-renamed to a `brand_welcome` row).

### Checkout-page copy — the gift is announced, never advanced

`POST /v1/checkout-sessions` payment mode carries `custom_text.submit.message` = `welcomeCompletionCheckoutNotice(offer)`, telling the buyer the free credits are still coming. The SENTENCE is product-approved — do not reword it — but the two figures are substituted from the org's OWN offer, because they differ per cohort and quoting the wrong one would promise money we will not grant. `$25/$25` renders byte-identically to the string this service shipped before ("You get $25 in free credits. $5 now, the rest once your payments reach $25.") and there is a test pinning that; `$400/$400` renders the $400 wording. The `$5` is a literal on purpose (the welcome gift is $5 for every cohort). The notice is deliberately withheld from an ineligible org and from one already fully gifted (it would be a lie). Stripe caps `message` at 1200 chars.

`decideCheckoutWelcomeNotice(orgId)` returns that string or null. It takes ONLY the org: it no longer needs the paid-topups sum or the checkout amount, because nothing about the charge depends on it any more.

**REMOVED — do NOT reintroduce the up-front checkout discount.** The route used to advance the whole entitlement as a pre-applied Stripe coupon (`discounts: [{coupon}]`, gated on `WELCOME_DISCOUNT_COUPON_ID`), so a first-ever checkout of at least `entitlement + trigger` was charged less and the credit landed immediately. Deleted along with `minDiscountedCheckoutCents`, `welcomeCompletionCodeExists`, the `applyDiscount`/`couponId` fields, and the `discounts` field on the checkout-session body.

The floor was the whole safety property: the post-discount charge still had to reach the trigger that EARNS the gift, or the discount handed over credit nobody paid for. At the $400 offer that floor is $800 — far above any real first checkout (onboarding charges roughly one day of budget) — so the branch had been **unreachable for every new signup** long before it was removed, and the grandfathered $25 cohort is the only one that could ever have hit it. The promise is served by `settleWelcomeCompletion`, on the path onboarding actually uses.

Two removal guards pin it: a first checkout at each cohort's old floor ($50 grandfathered, $800 new) must carry no `discounts` and must carry the notice instead. If you are tempted to bring the discount back, the thing to weigh is that it is the one place a buyer can be handed credit before the payment that earns it has cleared.

**`allow_promotion_codes` is gone and must not come back either.** It was enabled for a single journalist comp (that is done). Nothing in this service discounts a charge any more.

## Billing/runs ownership target

- **Billing-service** owns: local promo grants (`local_promos`), topup config (`billing_accounts.topup_amount_cents`, `topup_threshold_cents`).
- **Stripe-service** owns: Stripe customers, payment methods, payment intents, refunds, checkout sessions, billing portal sessions. Mirror DB synced via webhooks + boot back-fill.
- **Runs-service** owns: run-level usage truth. `spent_cents` from `GET /internal/org-usage-total?org_id=...` includes platform `actual + provisioned` costs, excludes canceled and `org`/BYOK costs.

Billing never duplicates Stripe state and never persists run-level usage rows.

## Fractional cents

`local_promos.amount_cents` is `numeric(16,10)`. Drizzle returns it as a JS string — never cast with `Number()` for math (precision loss). Use the `addCents/subCents/cmpCents/isDepleted/gte` helpers in `src/lib/cents.ts` (Decimal.js-backed, precision 50). `parseFloat` is for display only.

`payment_intents.amount_received` from Stripe is **integer cents** (Stripe's `amount` minor unit). Sum returns a `Decimal.toFixed(10)` string for arithmetic-compatibility with the helpers above.

## stripe-service integration shape

`src/lib/stripe-service-client.ts` only calls Stripe-shape primitives. stripe-service deliberately exposes no billing-specific shortcuts.

**⚠️ Treat stripe-service as PROD-ONLY unless you have just checked otherwise — assume nothing Stripe-touching can be verified on staging.** When this was written, staging ran no stripe-service at all and billing-service staging carried **no `STRIPE_SERVICE_URL` / `STRIPE_SERVICE_API_KEY`**; that was measured on Railway, which is gone, so the finding is history rather than a live fact. The way to know today is to read billing-service's staging env on the box and see whether those two vars are set (the old `railway link … --environment staging` probe no longer resolves anything). Until you have, plan as if they are absent — the failure mode this guards against is believing a staging run exercised Stripe when it could not. So for anything on a Stripe path (checkout, account funds, reload, the paid-topups sum), a `staging` merge is a **code waypoint only**: CI green is the whole of "staging is green", and real behavior is first observable after the prod promote. Plan the verification step accordingly, and do NOT set a Stripe object id (coupon, price, webhook) as a staging env var expecting it to be exercised — Stripe object ids are also mode-scoped (a live-mode coupon in a test-mode env is simply wrong).

- **Two read surfaces, split by whether an end-user is in context:**
  - **Real-user paths** (`GET /v1/accounts`, `POST /v1/customer_balance/usage_apply` direct compose, `redeem`, `checkout`, `reload`): customer fetch is **org-implicit** via `GET /v1/customers?limit=1` (resolved server-side from `x-org-id`). **stripe-service still REQUIRES `x-user-id` on these `/v1/*` reads (its header validation 400s without it) even though the lookup keys on `x-org-id` only** — so any identity passed to `getCustomerByOrg`/`sumSucceededTopupsForCustomer`/`hasAttachedCardPm` MUST carry `x-user-id`. Tests that mock these do NOT catch a missing `x-user-id` — it 500s only against the live service. **No READ here is reached without an end user any more**: the `transfer-brand` admin op used to send an `INTERNAL_IDENTITY` sentinel to get past this gate and has moved to the user-less surface below, so there is no remaining "fabricate an identity to satisfy a read gate" caller. The all-zeros `x-user-id` still means *the platform is the actor* on a WRITE this service genuinely performs (promos, credits, the month-end sweep reload) — that is a design choice and stays. Do not reintroduce it to get past a read gate.
  - **Brand-transfer path** (`POST /internal/transfer-brand`): `listAllCustomersForOrg` / `setCustomerMetadata` send **X-API-Key ONLY — no org, no user, no sentinel** (stripe-service v0.34.0, org / customer id in the path). See "transfer-brand SS-side semantics".
  - **Balance path** (`computeBalance` → affordability gate + dunning scheduler + authorize): reads stripe-service via the **user-less, org-keyed `/internal/<resource>/by-org/{orgId}` routes** (stripe-service#77/#79) — `fetchOrgCustomer` / `sumSucceededTopupsForOrg` / `hasChargeablePmForOrg` send **X-API-Key + org ONLY: NO `x-user-id`, NO sentinel**. There is no end-user on this path, so no fake identity is invented. `computeBalance(orgId)` takes no `identity` arg (the runs-service `/internal/org-usage-total` read needs only `org_id`). **Never reintroduce an `x-user-id` sentinel on the balance path** — that was the v0.31.1 band-aid (PR #176/#178), superseded once stripe-service shipped the user-less surface. The `/v1/*` real-user reads above are a SEPARATE surface — do not collapse `computeBalance` onto them, and do not move the `/v1/*` callers onto `/internal/*by-org`.
  - **Platform-stats path** (`GET /public/stats/billing`, `getStats()`): sends **NO identity at all — no org, no user, no sentinel**. stripe-service serves it as a PUBLIC route with no service auth and no identity middleware, so it reads neither header; it is a cross-org aggregate and there is no org or user behind the request. The zero-uuid pair this used to send was invented purely to satisfy a gate that does not exist, and both values were discarded on arrival while the fabricated org id sat in an audit log. `getStats()` takes no `identity` argument — do not add one back.
- Balance is derived from the Stripe customer object: `balance_cents = -customer.balance` (sign-flip, Stripe convention is `balance > 0` = customer owes).
- `has_payment_method` is derived from whether the customer has ≥1 attached **chargeable** PM — a `card` **or** a `link` PM (`hasAttachedCardPm` → `GET /v1/payment_methods?type=card`, then `type=link` if no card). **Link PMs ARE chargeable off_session** when passed as an explicit `payment_method` id (Stripe documents `off_session:true, confirm:true` on a saved `type:link` PM exactly like a card — https://docs.stripe.com/payments/link/save-and-reuse). A normal Checkout setup-mode flow offers card+link and saves `type:link` for Link-enabled emails, so a **card-only gate wrongly reported "no payment method"** for those orgs and 400'd `PATCH /v1/accounts/auto_topup` forever (v0.29.1 fix, GH #162). It deliberately does **not** read `customer.invoice_settings.default_payment_method`: Stripe leaves it null after `setup_future_usage`, AND the **default-PM *fallback* path** (PI with no explicit `payment_method`) genuinely fails for Link (the original DIS-43 400) — but that is the fallback, not an explicit link-PM charge. We list PMs by type and pass an explicit id instead. This mirrors exactly what `reload.ts` charges (first card, then link fallback). The same `hasAttachedCardPm` gate fronts auto-reload in `authorize` + `usage_apply` and the `PATCH /v1/accounts/auto_topup` PM requirement. Fail-loud: a stripe-service error propagates (502); only an empty card AND link list → false.
- Reload is composed billing-side via `POST /v1/payment_intents` with `confirm:true, off_session:true` + `Idempotency-Key` header. Stripe status flattened to `{succeeded|failed}` in `src/lib/reload.ts`.
- Balance transactions list uses the org-implicit `GET /v1/balance_transactions` (no customer id needed).

## transfer-brand SS-side semantics

`POST /internal/transfer-brand` re-points an org's solo-brand Stripe customers via the **user-less** stripe-service surface (v0.34.0) — `GET /internal/customers/by-org/{orgId}/all` then `POST /internal/customers/{id}/metadata`, both **X-API-Key only, no identity headers** (the org / customer is named in the path).

**It was dead in prod until this shipped.** The list step used to call the identity-guarded `GET /v1/customers?metadata[org_id]=…` with nothing but a zero-uuid `x-user-id`, so stripe-service answered `400 {"error":"Missing required header: x-org-id"}`, the handler threw, and the transfer never completed — every later step was unreachable. Same class as stripe-service#77 (a machine caller with no end user pointed at a per-user gate) on a route nobody re-checked after that issue shipped. **The fix is the user-less surface, never a fabricated org id alongside the fake user id.**

- **List:** the whole set in ONE call, resolved from stripe-service's own `org_id` column (not a metadata filter), with no pagination — there is nothing left to page. Completeness is load-bearing: 4 prod orgs hold more than one Stripe customer (orgs predating the idempotent `POST /v1/customers`), and a transfer that only saw the newest would silently strand the others on the source org.
- **Brand filter (client-side, and it stays here):** `customer.metadata.brand_id` is treated as a **comma-separated UUID string**. Only customers whose `brand_id` parses to exactly one UUID matching `sourceBrandId` are patched. Multi-brand customers are skipped and named in a warning log (patching them would orphan the co-brands). Mirrors the `local_promos array_length(brand_ids,1)=1` solo-brand semantics on the billing-DB side. **This is business knowledge about brands and promos — stripe-service has none of it and must not acquire any.** It hands over the customers and performs the write; this repo decides which ones.
- **Write:** `setCustomerMetadata(id, metadata)` sends the FINAL metadata shape (`org_id=targetOrgId`, plus `brand_id=targetBrandId` when provided). stripe-service forwards it verbatim to Stripe, so Stripe's semantics apply — keys are MERGED and a key set to the empty string is deleted; other keys are preserved without restating them. It re-mirrors immediately and resolves the org from the UPDATED object, so the mapping lands on the new owner in the same request.
- **Partial failure:** if a write fails mid-loop, returns 502 with `{ partial: { stripe_service_customers_patched, total_targets } }`. The metadata write is idempotent — the caller can resume.

The same CSV convention applies to the `x-brand-id` header forwarded by workflow-service for multi-brand campaigns.

## Off_session auto-reload — country eligibility (India / RBI e-mandates)

**Off_session auto-reload is IMPOSSIBLE for cards issued in some countries, and Stripe cannot fix it through the path billing uses. India is the confirmed, prod-observed case (GH #220).** Hard Stripe facts (verified against docs 2026-06-27 — re-verify before changing this):

- An off_session reload on an India-issued card is declined: *"You must provide a mandate for off-session card payments made with cards issued in India."*
- India RBI e-mandates are registrable **ONLY via Stripe Subscriptions**, NOT via PaymentIntents or SetupIntents (https://docs.stripe.com/india-recurring-payments — explicit note). billing's wallet model = SetupIntent card capture (Checkout setup/payment mode) + raw off_session **PaymentIntent** reload (`src/lib/reload.ts`) → **no Stripe-supported way to register the mandate**. So adding `payment_method_options.card.mandate_options` to the capture call does NOT work: Checkout doesn't carry it, and even a SetupIntent (which has the field) does not create an India e-mandate. Do NOT reach for that "fix" again — it's a dead end for this architecture.
- Even via Subscriptions, India off_session carries a **26-hour pre-debit notification delay** + per-charge AFA above **~15,000 INR (~$180)**. "Top up NOW to keep a campaign running" is structurally impossible for India cards by ANY path. The product answer for India is **manual on-session top-up** (the existing one-shot Checkout payment + the dashboard Add Credit flow), NOT auto-reload.
- **Forward-only**: a card already saved without a mandate cannot be retrofitted (Stripe declines; needs customer re-auth). The fix only affects cards added after it shipped.

**What billing does (v0.40.0, GH #221):** detect the card's issuing country and make auto-reload coherently unavailable instead of attempting a doomed charge.

- `card.country` is **already on the wire** — stripe-service passes the Stripe PaymentMethod object through verbatim. NO stripe-service change is needed to read it.
- `AUTO_RELOAD_BLOCKED_CARD_COUNTRIES` + `isAutoReloadBlockedCountry()` + `getOrgCardCountry` (real-user) / `getOrgCardCountryByOrg` (balance path) live in `src/lib/stripe-service-client.ts`. **Blocklist = `{ IN }` only.** EEA is deliberately NOT blocked (its mandate is satisfied by `setup_future_usage` + SCA on the initial Checkout save, which already works — EU orgs auto-reload fine). Mexico / Brazil are listed by Stripe as agreement-requiring but the mechanism is unconfirmed and there is zero prod evidence — left out to avoid blocking orgs that may work. Extend the set ONLY when a decline is confirmed in prod.
- Enforced in BOTH reload paths so the UI "deactivated" state never contradicts backend behavior: `customer_balance/authorize` gates on `snapshot.autoReloadSupported` (from `computeBalance`), `usage_apply` gates on `snapshot.autoReloadSupported` from the same `computeBalance` snapshot — both **skip the reload** for a blocked country and fall through to depletion dunning (which prompts manual recharge). `PATCH /v1/accounts/auto_topup` rejects a blocked-country card (400, fail-loud) rather than storing config that never fires. `GET /v1/accounts` exposes `auto_reload_supported` / `auto_reload_unsupported_reason` / `card_country`, and forces `has_auto_topup=false` when unsupported.

## Threshold-based postpaid top-up (Google/Meta-Ads cadence)

Auto-topup is **postpaid on a derived tier ladder**, not a fixed daily charge. The balance is allowed to run NEGATIVE down to a credit-line floor; a fixed reload fires only when spend crosses that floor — so a $32/day org is charged ~every 1.5 days, not daily.

- **Derived tier** (`src/lib/topup-tier.ts`, `tierFor(cumulativePaidCents)`): pure function of the org's cumulative **succeeded topups** (the same `sumSucceededTopupsForOrg` / `sumSucceededTopupsForCustomer` sum already computed — NOT credited, promos excluded). Returns `{ thresholdCents (NEGATIVE floor), amountCents }`, magnitudes equal so one charge clears one crossed line. Ladder: `≥ $1000 paid → {-50000, 50000}` ($500 line); `≥ $200 → {-20000, 20000}`; else `{-5000, 5000}` ($50 start line). The line grows with trust. **No storage** — derived every read.
- **Stored `billing_accounts.topup_amount_cents` / `topup_threshold_cents` are ONLY the "auto-topup enabled" flag** (non-null ⇒ enabled). The effective `(amount, threshold)` come from `tierFor()` EVERYWHERE — reload math in `authorize` + `usage_apply`, and the account-read response. The `PATCH` request schema is unchanged (still `min(0)`); the negative threshold is derived + returned, never written through the route.
- **`authorize` (true postpaid):** sufficient (no reload) when `balance − required >= threshold` (floor). Below it, reload multiples of the tier `amount` toward `threshold + required`, then recheck against the floor. Orgs that can't be reloaded (no config / no card / blocked country) have **no credit line → floor `"0"`** (strictly prepaid) — the sufficiency + dunning gates behave as pre-postpaid for them.
  - **`required` is NETTED by the org's usage discount before this comparison** (`applyUsageDiscount(resolveRequiredCents(...), getUsageDiscountPct(orgId))`, right after resolve). `resolveRequiredCents` returns the **GROSS** costs-service list price, but a discounted org is charged the **NET** amount (runs freezes the discount per cost row) and `balance` is already net. Comparing gross `required` to a net `balance` over-reserves headroom for a discounted org and fires its auto-reload **early** (a 50%-off org triggered at −$25 instead of −$50). This is the **ONE** place billing applies the discount — it nets a forward CATALOG estimate, NOT the runs-netted usage, so it is not the double-discount trap the balance paths avoid. The netted `required` flows to the sufficiency check, the reload target, the recheck, the `campaign_authorize_costs` upsert, AND the response `required_cents`. `usage_apply` has no `required` (fires at `balance < threshold` flat), so it is unaffected.
- **`usage_apply`:** composes the balance from `computeBalance` (the SAME NET source as authorize — runs `net_spent_cents`, discount frozen at cost-write), then reloads when `balance < threshold` (negative floor), charging tier `amount` multiples toward the floor. It deliberately does **NOT** gate on the request's `spent_total_cents`: that value is the CALLER's **GROSS** usage total, and subtracting gross from credited understated a discounted org's balance by the discount amount → fired the auto-reload ~$56 early, charging a 50%-off org while its true NET balance was positive (bug #285). The body value is now a no-op hint (logged in the start trace only).
- **Dunning gate is threshold-aware** (`src/lib/cents.ts` `isDepleted(a, threshold="0")`, 2-arg): a depletion episode / T0 email opens ONLY when `balance <= threshold` (past the floor), NEVER on a normal negative balance within the line. `openDepletionEpisodeIfDepleted` takes `thresholdCents` (the derived floor for reload-capable orgs, `"0"` otherwise). This is also the structural root-fix for #170 (the balance-flutter duplicate-email bug): an enabled org running at ~0 never reaches the depletion path until it genuinely blows past the negative floor. The `credited`-rising recovery logic is unchanged; the dunning-tick follow-up gate stays at floor `"0"` (still-in-the-red check).
- Credit exposure is bounded by `|threshold|` of the current tier plus one run's overshoot.
- Onboarding / initial wallet-setup checkout is unchanged (seeds a positive buffer, lowers risk).
- `computeTopupCharge(currentBalance, target, unit)` (the shared reload-math: cents to charge in whole tier-`unit` multiples to lift the balance to `target`, rounding the multiple up) lives in `src/lib/topup-tier.ts` and is reused by `authorize` (target = `threshold + required`), `usage_apply` (target = `threshold`), and the month-end sweep (target = `"0"`). It was moved out of `customer_balance.ts` so all three paths share one source.

### Month-end forced top-up sweep (guarantee ≥1 charge/month)

A slow spender whose balance never crosses the floor within a calendar month would go the whole month un-charged (Google/Meta Ads sweep any outstanding spend on the monthly bill date regardless of amount). `src/lib/month-end-sweep.ts` fixes this: `runMonthEndSweep(now = new Date())` settles every reload-capable org back to `>= 0` once a month.

- **Trigger:** runs from the SAME hourly dunning scheduler (`dunning-scheduler.ts` tick, post-`listen()` — never the boot path), isolated in its own try/catch so a sweep failure never blocks dunning and vice-versa. Self-gates on `isSweepTick(now)` = `isLastDayOfMonth(now) && getUTCHours() === SWEEP_HOUR_UTC` (23) — a single date check on every other tick.

  **⚠️ The HOUR is part of the gate, and removing it re-creates a prod bug.** The gate was day-only at first, which reads as harmless because the sweep's idempotency is "once the settle lands the org reads non-negative, so later ticks skip it" — but that only holds for an org that STOPS SPENDING. An org still consuming goes negative again within the hour, so a day-only gate re-charged it on **every remaining hourly tick of the last day**. On **2026-07-31** one org was billed three times in seven hours (**$500** → $174.07 refunded, then **$1.00**, then **$20.00**), every amount a correct deficit and the cumulative total correct. The bug is charge FRAGMENTATION, not over-collection, which is exactly why it survived both same-day fixes above and was reported by Kevin from his own card statement ("Je viens de recevoir ces 2 transactions. Normal???"), not by any test or metric.

  Restricting to one tick needs **no new state**, and a missed sweep is not lost revenue: the balance is cumulative, so the next month's sweep collects the larger deficit, and in-month exposure stays bounded by the postpaid credit-line floor (whose own reload keeps firing throughout). Residual, accepted: a restart inside the sweep hour re-ticks 60s after boot, and the Stripe key collapses that only while the deficit is unchanged. Do NOT "fix" a missed month by widening the gate back to the whole day, and do NOT add a `last_swept_month` column — the whole point is that the cheaper subtract holds.
- **Selection:** auto-topup-ENABLED accounts (`topup_amount_cents` AND `topup_threshold_cents` non-null), then per-org reload-capability re-checked against the live snapshot (chargeable card + non-blocked issuing country — mirrors the `usage_apply` guards). Only a `balance < 0` org is charged; a non-negative org owes nothing, and anything already past the floor is owned by the normal floor-crossing path.
- **Charge:** ONE `reloadOffSession` (via `coalesceReload` + a 30s timeout) of `computeSettleCharge(balance)` — **EXACTLY the outstanding amount**, settling the balance to exactly 0. No end user on this path and none is invented: the neutral charge is service-authenticated with the org in its path, so the all-zeros `x-user-id` the sweep used to carry (to satisfy the `/v1` reload primitives) is gone with the primitives themselves.

  **⚠️ The sweep does NOT charge tier multiples, and must never go back to doing so.** It originally called `computeTopupCharge(balance, "0", tierFor(paidTopups).amountCents)`, i.e. whole multiples of the org's $50/$200/$500 tier reload amount. That is right for the IN-MONTH reload paths (`authorize` / `usage_apply`), where a charge buys back one crossed notch of the credit line — but on the monthly settle there is no line to restore, only a balance to zero, so a multiple over-collects from every org whose deficit is smaller than one notch. On **2026-07-31** it billed a −$9.61 org **$50**, a −$10.69 org **$50**, a −$20.38 org **$50** and a −$325.93 org **$500** — **$283.39** over-collected across four orgs in one tick, refunded afterwards. `computeSettleCharge` (in `month-end-sweep.ts`) is the whole fix: `ceil(−balance)` in whole cents, `0` when non-negative. The sweep no longer imports `tierFor`/`computeTopupCharge` at all.

  Fractional cents round **UP** — Stripe charges whole cents, and rounding down would leave the org a fraction negative and re-arm the sweep next month for pennies. A deficit below **`STRIPE_MIN_CHARGE_CENTS` (50)** cannot be charged at all (Stripe rejects `amount_too_small`), so it is logged and rolls into the next month's sweep; it counts as `skipped`, never `failed`.
- **Idempotency (NO new storage):** the PRIMARY guard is the balance re-check — once the settle lands, `credited` rises past `usage` and the org reads non-negative, so later same-month ticks skip it. On top of that, `sweepIdempotencyKey(orgId, bucket, chargeAmountCents)` collapses a same-month double-charge across the mirror-sync-lag window / multiple replicas: a re-tick before the charge is mirrored reads the same balance, computes the same amount, and replays the same Stripe invoice (every tick of the sweep hour falls inside Stripe's ~24h key retention).

### Taking money names no vendor — `reloadOffSession` (`src/lib/reload.ts`)

The automatic reload asks stripe-service for a **charge**, not a document: `POST /internal/charges/by-org/{orgId}` with an amount, a currency, a reason and the caller's `Idempotency-Key`. stripe-service resolves which acquirer holds the org's card and answers in ONE shape whatever it resolved (`ChargeResult`), so an org can be moved onto a different acquirer with nothing changing here.

It used to ask for an **invoiced** charge, whose whole purpose was producing a finalized Stripe invoice with a hosted PDF. That is a Stripe capability. An acquirer with no invoice object cannot serve an org through it, and must not start returning a fabricated one — so the call site moved to the surface that answers the question it actually has: take this much money, off-session, did it work.

- **No vendor knowledge, and none may come back.** Nothing in this repo names an acquirer, branches on one, or stores a per-org acquirer setting. `ChargeResult.acquirer` is diagnostic only — reading it to decide anything is the bug this design removes. If a change here seems to need one, the producer contract is wrong; say so rather than work around it.
- **`hosted_document_url: null` is NOT a failure.** It means "this acquirer has no such thing". Success is read from `status` alone. Never synthesise a document, and never treat its absence as a decline.
- **Billing resolves NO payment method.** The old invoiced reload picked an explicit card (then a link) PM billing-side and passed its id — Stripe-object knowledge that is gone with it. Which saved card to charge belongs to the acquirer that holds it. (`hasAttachedCardPm` / the blocked-country gate are a different question — *can* this org be auto-reloaded at all — and are unchanged.)
- **Idempotency is unchanged**: the same `reloadIdempotencyKey` / `sweepIdempotencyKey` the callers already computed rides as `Idempotency-Key`, so a retried top-up collapses onto the first charge.
- **`ReloadOutcome.reference`** is the acquirer's own id for the charge (it was `payment_intent_id`, which named one vendor's object). Nothing reads it to decide anything; it exists for support and reconciliation.
- **Accounting is unchanged**: stripe-service mirrors a succeeded charge on the same request, so the paid-topup sums count the top-up immediately, whichever acquirer ran.
- **Interactive checkout is untouched** — only the automatic, off-session charge moved.

### The failure notification fed the loop it was reporting (prod 2026-08-29)

**Sending `credits-reload-failed` AUTHORIZES CREDIT on the very org it is about.** The email path is org-billed, so the notification re-enters `POST /v1/customer_balance/authorize`, which finds the org below its floor, attempts another reload, gets another decline, and sends another notification. Measured over 71 minutes on one org: **2,939 authorizations, 2,938 of them attributed to `transactional-email-service / email-credits-reload-failed`, and ZERO to product traffic.** The seed was a single customer budget change (whose own notification is also org-billed); after that the loop needed no external traffic at all. The smoke alarm was wired to the fuse it had just blown.

Two things made it invisible. The per-minute time bucket in `reloadIdempotencyKey` collapsed those 2,939 authorizations into **72** Stripe charges, so the observable rate looked like a tame one-per-minute; and the loop is entirely internal, so no caller ever reported anything.

**The root cause is not ours to fix and must not be papered over here.** A platform lifecycle notification ("you are out of credit", dunning) being billed to the org it warns is circular by construction; that classification belongs to the email path. What billing owns is refusing to *drive* the loop:

- the **backoff** (`coalesceReload`) is the structural stop — a second authorize inside the cooldown gets a synthetic outcome and never reaches Stripe. Prod, immediately after v0.66.1: **2,939 authorizations became 7.**
- the **send is gated on the failure streak** — `consecutiveReloadFailures(orgId) <= 1`, so a customer is told on the first failure of a streak and not again until a charge succeeds. This gate is on the THROW branch specifically, because a declined off_session charge arrives as a throw (stripe-service answers 402) and therefore carries no outcome object to read `backoffSkipped` from. The settled-failure branch has its own guard. **Both branches need one** — guarding only the settled branch leaves the loop fully open, since the declining-card case is exactly the throw.

**Never send a money-failure notification from a path that a money-failure notification can re-enter, without a guard that terminates.** Before adding any send to the authorize path, ask what happens if that send authorizes.

  **⚠️ The charge amount is IN the key, and must stay there.** stripe-service derives one acquirer key per step from billing's single key, and an acquirer rejects a replayed key whose parameters changed. `invoiceItems.create` carries the amount — so an amount-INDEPENDENT key makes a second sweep charge of a DIFFERENT amount in the same month structurally impossible, and the org silently goes uncollected until the next month's bucket. Worse, step 1 `invoices.create` carries no amount, so it REPLAYS the first attempt's invoice, which may since have been voided or paid.

  That fired on **2026-07-31**, hours after the over-collection fix above: the corrected amounts collided with the keys their own over-charges had burned. `eligible=19 charged=0 skipped=16 failed=3` — every org whose first attempt that month had already used the key (the one whose $500 invoice declined, plus the two card orgs whose refunds put them back in the red). The declined org's replayed invoice was void by then, so no key fix short of changing the WHOLE key would have worked. Residual, accepted: if a charge lands, is not yet mirrored, AND usage accrues before the next hourly tick, the deficit differs and a second charge is possible — the balance re-check is the guard, and the mirror is webhook-driven (seconds) against an hourly tick. The alternative is what cost three orgs a month.
- **Fail-loud per org, isolated:** a per-org error is logged (`console.error("[billing-service] month-end sweep failed for org …")`) and skipped; one unreachable org never blocks the rest (same shape as `runDunningTick`).
- **No cost declaration:** a reload collects the org's OWN money via Stripe — not a metered platform cost, exactly like the `authorize` / `usage_apply` reloads. No runs-service cost row.

All three credited/usage/balance endpoints fail loud (502) when runs-service or stripe-service is unreachable.

`balance_cents` and `actual_balance_cents` deliberately differ when the org has open provisioned holds. `balance_cents` is spendable availability and subtracts actualized costs plus provisioned holds so authorization cannot overspend. `actual_balance_cents` subtracts only actualized costs, so the dashboard does not show a hold as money already spent.

Composition (`src/routes/accounts.ts:composeAccountFunds`):
1. `getCustomerByOrg(identity)` → Stripe customer (for `id`)
2. `sumSucceededTopupsForCustomer(identity, customer.id)` → paginates `GET /v1/payment_intents?customer=cus_X` and sums `amount_received − amount_returned` where `status='succeeded'` (refunds + lost disputes netted out — see "Refunds and lost disputes")
3. `sumLocalPromoCreditsForOrg(orgId)` → SUM `local_promos.amount_cents`
3b. `settleFreeCreditPromises(orgId, paidTopups)` → grants the welcome-completion gift if earned (paid topups are its trigger and we already hold them here), then the freshly-granted amount is folded into the promo sum rather than re-querying. The grandfather check lives inside it and asks stripe-service for the as-of-launch figure only for a pre-launch org that has crossed the trigger, so it costs no extra Stripe read on the normal path. See "Welcome-completion gift". Fails loud → 502.
4. `fetchRunsOrgUsageTotal(orgId, identity)` → reads runs-service **`net_spent_cents`** (the frozen-NET usage total, `SUM(COALESCE(net, gross))`), NOT the gross `spent_cents`. Returned to callers as `spent_cents` (billing's "usage" = the discounted amount the org owes).
5. `fetchRunsOrgActualUsageTotal(orgId, identity)` → reads runs-service **`net_total_expected_cents`** (the frozen-NET actualized total), NOT the gross `total_expected_cents`, from actualized platform costs only.

> **Why net, not gross (bug #262):** the per-org usage discount is frozen per cost row at write time IN runs-service (gross + net stored). billing reads the NET org totals and subtracts them verbatim — the discount is applied exactly once (in runs), never re-applied here, and pre-discount rows read net == gross so it is non-retroactive. Reading the gross `spent_cents`/`total_expected_cents` fields (the pre-#249 wiring) left the dashboard Available + Confirmed/Provisioned lines at GROSS while the brand Overview showed net. ALWAYS read the `net_*` runs fields for balance composition.
6. `hasAttachedCardPm(identity, customer.id)` → `has_payment_method` (≥1 chargeable PM: card or link)
7. `getOrgCardDisplay(identity, customer.id)` → `{country, brand, last4, expMonth, expYear}` (one Stripe read of the first card PM) → `card_country`/`card_brand`/`card_last4`/`card_exp_month`/`card_exp_year` (display-only, null when no card PM) → `auto_reload_supported = !isAutoReloadBlockedCountry(card_country)` (see "Off_session auto-reload" below)
8. `getUsageDiscountPct(orgId)` → `usage_discount_pct` (dashboard banner only; see "Per-org usage discount"). Does NOT enter the balance math — runs-service already served net usage.
9. `credited_cents = paid_topups + local_credits`; `balance_cents = credited_cents − usage`; `actual_balance_cents = credited_cents − actualized_usage`. runs-service usage is already NET of the discount, so billing subtracts it verbatim (no discount applied here). The two halves are also exposed raw as `credited_paid_cents` / `credited_gifted_cents` so the dashboard never computes a money figure in the browser.

```jsonc
    { "period": "2026-05-01", "credited_cents": "25000.0000000000", "revenue_cents": "23000.0000000000" }
  ],
  "weekly_growth": [ ... ]
}
```

Growth rows expose `credited_cents` and `revenue_cents` only, both NET (they read stripe-service's per-bucket `net_cents`). A return is bucketed in the period it HAPPENED, not the period of the payment it reverses — stripe-service does not back-date, so a past bucket is never rewritten. Total consumed lives in runs-service. Endpoint returns 502 if stripe-service unreachable.

## Per-org usage discount (frozen at cost-write in runs-service — billing does NOT apply it)

Platform staff can give an org a percentage discount on ALL its platform usage. A discounted org effectively pays `(1 − discount_pct/100)` of its GROSS usage. **The discount is applied EXACTLY ONCE, at cost-declaration time, inside runs-service** (which stores a gross and a net amount per cost row, netting once at write). billing-service therefore **STORES the percentage, SERVES it (to runs-service + the dashboard), and NEVER applies it at balance composition** — runs already serves a net usage figure, so billing subtracts that verbatim. Applying it here again would DOUBLE-discount. It is NOT a Stripe coupon and NOT bonus/matching credits.

> **Sole billing-side application — the `required` ESTIMATE in `authorize` (NOT a balance path).** `authorize` reserves the next run's cost via `resolveRequiredCents`, which returns the **GROSS** costs-service list price — costs-service does NOT know the org discount, so that estimate is never netted upstream. The run, when it executes, is charged NET (runs freezes the discount). Since the sufficiency + reload-trigger comparisons are `balance_net − required`, `authorize` MUST net `required` first (`applyUsageDiscount(required, getUsageDiscountPct(orgId))`), or a discounted org over-reserves and auto-reloads early (the −$25-instead-of-−$50 bug). This is NOT the double-discount trap: it nets a **forward catalog estimate**, never the runs-netted usage — a single application of the discount to a quantity runs never touched. `usage_apply` (no `required`) and every balance-composition site stay untouched.

> History: PR #246 first applied the discount ON READ at every balance-composition site. The architecture then moved the netting into runs-service (single application at write). This rework (superseding #246 on staging) REMOVED billing's read-side application; the storage + CRUD + exposure are kept. Never reintroduce an `applyUsageDiscount(usage, pct)` multiply on a balance path (usage/balance composition) — that is the double-discount bug. Netting the `authorize` `required` ESTIMATE is the ONE allowed application (it nets the gross catalog estimate, not usage).

**State:** one table, `org_usage_discounts` (migration `0026`, hand-journaled) — `org_id` PK, `discount_pct integer` (DB CHECK 0..100), `set_by text` (staff email), `set_at`, `created_at`. ONE row per org; **absence of a row = null = no discount**. Replaceable (upsert on `org_id`), removable (DELETE → null). `src/lib/usage-discount.ts` owns the read/set/remove. (`applyUsageDiscount(grossCents, pct)` still lives there for tests/reference but is NOT called on any balance path.)

**Where the pct is READ (never to reduce a billing-side balance):**
- `GET /internal/accounts/by-org/:orgId/usage-discount` (`src/routes/internal.ts`) — the user-less read runs-service calls at cost-write to freeze the discount onto each cost row (and features-service #510 reads for net-priced metrics). Returns BOTH `discount_percent` (int 0–100, the features-service reader) AND `discount_pct` (fraction 0–1, the runs-service reader — its `parseDiscountFraction` fail-loud 422s if absent, matching its `usage_discount_pct numeric(9,8)` fraction column). No discount → both `0`, NOT null/404. Two consumers, two field names + scales → serve the UNION so neither has to change. Service-auth, orgId PATH param. **Never drop `discount_pct` again — #250 conformed to features' name only and 502'd every runs-service cost write (missing `discount_pct`), fleet-wide.**
- `composeAccountFunds` (`src/routes/accounts.ts`) for `GET /v1/accounts` (+ `balance`, `auto_topup`): reads the pct only to expose `usage_discount_pct` for the dashboard banner. `balance_cents`/`actual_balance_cents` subtract runs' net usage directly; the pct does not enter that math.
- Staff CRUD `GET/PUT/DELETE /v1/usage-discount` (`src/routes/usage_discount.ts`).

`computeBalance` (`src/lib/balance.ts`), `usage_apply`, authorize, the dunning scheduler, month-end sweep, affordability, and `GET /internal/accounts/by-org/:orgId/balance` all subtract runs-service usage (already net) verbatim — none read or apply the discount. Removing the discount restores full pricing on NEW cost writes (not retroactive). Fail-loud: an out-of-range percentage is rejected at both the Zod route schema and `setUsageDiscount` (`InvalidUsageDiscountError`) — no clamp, no default.

**Cross-service contract:** runs-service is the discount OWNER at write time. It reads billing's `GET /internal/accounts/by-org/:orgId/usage-discount` and applies the pct once per cost row (gross + net stored). billing only READS runs' net usage — it does NOT modify runs' gross ledger.

**Follow-up (other repos, not built here):** runs-service consuming the internal discount read + storing gross/net per cost row; api-service gateway proxy gating `/v1/usage-discount` to staff; admin-console UI to read/set/remove; dashboard banner rendering from `usage_discount_pct`.

## Per-brand daily budget (pacing ceiling — NOT affordability)

Each org+brand pair carries exactly ONE current **daily budget** — the per-day spend ceiling for that org's active work on that brand. A shared brand used by multiple orgs has independent budget rows. A scalar, mutable: changing it re-paces future work on the consumer's next loop. This is an **allocation / pacing** concept ("how much should THIS org spend for THIS brand per day"), DISTINCT from the org credit balance/affordability ("can the org pay right now") — the two never mix. billing-service only **stores + serves** this value; **enforcement** (summing today's spend vs the ceiling, stop-when-exceeded) is the consumer's job.

**State:** one table, `brand_daily_budgets` (migration `0022`, org-scoped by migration `0024`, hand-journaled) — composite PK `(org_id, brand_id)`, `daily_budget_cents numeric(16,10)`, `updated_at`. One row per org+brand, upserted in place (`ON CONFLICT (org_id, brand_id) DO UPDATE`). `src/lib/brand-budgets.ts` owns the upsert + read.

**Change history (migration `0027`, hand-journaled):** `brand_daily_budget_changes` — append-only, `id bigserial` PK, `org_id`, `brand_id`, `daily_budget_cents numeric(16,10)`, `changed_at`. ONE row inserted per `PATCH` write, in the SAME transaction as the `brand_daily_budgets` upsert (so a change is never stored without its dated history entry). **Forward-only** — no backfill of pre-feature changes (never captured; a fabricated timeline would be wrong). Read by `GET /internal/brands/:brandId/daily-budget/history` (features-service customer-health board timeline), oldest-first (`ORDER BY changed_at, id`). The current-value read is unchanged (still serves only the latest). `upsertBrandDailyBudget` + `getBrandDailyBudgetHistory` in `src/lib/brand-budgets.ts`.

- **Read** (`GET /internal/brands/:brandId/daily-budget`, `src/routes/brand_budgets.ts`, **api-key + `x-org-id`; no user context**): services call this with the internal org UUID and brandId. No row for that org+brand → `dailyBudgetCents:null` (a legitimate unset state, distinct from an explicit `0` pause), even if another org has set a budget for the same brand. 400 on a non-UUID brandId or missing/invalid `x-org-id`.
- **Write** (`PATCH /v1/brands/:brandId/daily-budget`, requireOrgHeaders): the user via the gateway. Value keyed by `(x-org-id, brandId)`. `dailyBudgetCents` validated via `parseNonNegativeCents` (allows 0, rejects negative; fractional cents OK). A subsequent org-scoped read reflects the latest write.

### Staff notification on every real change (`src/lib/brand-budget-notification.ts`)

A customer changing a brand's daily budget is the most business-critical action we can observe (a drop to zero is a churn signal, a raise is expansion, the first-ever value is the deal size), and this service owns the ONLY write path for that value in the whole fleet — so it is the only place that can see every change. `PATCH` fires the `brand_daily_budget_changed` event through the existing fire-and-forget `sendEmail` client right after a successful write.

- **`brand_daily_budget_changed` is byte-equal in THREE places** and must stay so: the event key billing sends, the template `name` registered at boot in `src/instrument.ts`, and the entry in transactional-email-service's `ADMIN_NOTIFICATION_EVENTS` (its PR #108). That service resolves a template by `name == eventType`, so renaming one of the three silently 404s the send. The template row now imports `BRAND_DAILY_BUDGET_CHANGED_EVENT` from the sender instead of retyping the string, so two of the three can no longer drift. (See "Boot-time email template registration" — the registration itself was dead code when this shipped, so the notification was mute in prod until v0.57.1.)
- **No staff address here, and no second recipient list.** transactional-email-service routes the event to the staff list it already owns (`ADMIN_EMAILS`) instead of to the customer resolved from `x-user-id`, and enriches `metadata.email` with the acting user's email **only when the caller supplies none**. So billing passes `email` through when the gateway forwarded `x-email`, and otherwise OMITS it deliberately (do not fill it with a placeholder — that would suppress the enrichment). The event sits in no dedup set: every change notifies (measured prod volume ~16 writes / 60 days, so no batching / rate-limiting / dedup table is warranted).
- **The "from" value is read INSIDE the write transaction** — `SELECT … FOR UPDATE` in `upsertBrandDailyBudget`, which now returns `{ row, previousDailyBudgetCents }` — so a concurrent write can never make the reported previous value stale. No new table, column, flag or "already notified" accumulator: the pre-write value in that transaction is the whole mechanism. (A first-ever set has no row to lock, so two concurrent first-ever writes for one org+brand would both report "unset"; the stored value still resolves correctly via `ON CONFLICT`, and at ~one write every four days that race is not worth a table lock.)
- **What counts as a change:** a different value, or a first-ever set (`previousDailyBudgetCents === null` → `previousBudget: "unset"`). A re-save of the SAME value sends nothing — compared with `cmpCents`, so `5000` vs `5000.0000000000` is correctly a no-op. The history row is still written on every `PATCH`; journaling is unchanged.
- **Rendering** (`formatDailyBudget`): whole dollars per day (`$50/day`) — a daily budget is a whole-dollar configuration value, so fractional cents never print. `0` renders `paused ($0/day)`, never "changed to 0". `null` renders `unset`.
- **Strictly fire-and-forget — the documented exception to fail-loud.** `notifyBrandDailyBudgetChanged` never throws (its own `try/catch`, plus `sendEmail`'s `.catch`) and is never awaited, so an email service that is down, misconfigured, slow, or erroring cannot change the endpoint's status code or body. A customer-facing write must not gain a failure mode from a staff notification.
- Deliberately out of scope: staff SMS (a transactional-email-service fan-out gated on a Twilio number purchase) and the per-campaign daily budget owned by campaign-service.

**Follow-ups (other repos, not built here):** api-service gateway proxy for the user `PATCH`; campaign-service reads the internal `GET` per loop + enforces; dashboard UI to set it.

### Per-FUNNEL ceilings — the brand budget, split by sales funnel (`src/lib/brand-funnel-budgets.ts`, migration 0035)

A brand sells through several SALES FUNNELS; brand-service owns that vocabulary and its four keys are `reply_meeting`, `visit_meeting`, `visit_signup`, `visit_form`. One pot funds all of them, so a customer selling both a $200 self-serve plan and a $20k contract cannot say "spend $1/day chasing purchases and $24/day chasing meetings". `brand_funnel_daily_budgets` (`daily_budget_cents numeric(16,10)`, `updated_at`) records ONE ceiling per funnel — since migration 0036 its PK is `(org_id, brand_id, funnel_key, feature_slug)` and the per-funnel figure is the SUM of that funnel's acquisition channels (see "One ceiling per (funnel, ACQUISITION CHANNEL)" below).

**The load-bearing invariant: `getBrandDailyBudget` keeps its shape and answers the SUM of the ceilings.** The launch gate, the runway warnings, the credit alerts, the Overview tile and campaign-service's budget propagation all read that one number, and not one of them changed. **Never let a consumer recompose the sum** — that is exactly how two surfaces start disagreeing about the same figure. `GET /internal/brands/:brandId/funnel-budgets` returns the same total alongside the per-funnel rows for the same reason.

- **NO BACKFILL, for a brand selling through SEVERAL funnels.** Splitting one brand-level budget across them would invent numbers the customer never stated. A brand that never set per-funnel ceilings reads its `brand_daily_budgets` row exactly as before, which is what made this shippable ahead of every consumer.

  **The rule never covered a brand selling through exactly ONE funnel** — there the whole ceiling belongs to that funnel by construction, so there is nothing to invent, only an attribution to record. Leaving it unrecorded is a live incoherence: brand Settings renders `$0/day` on the funnel of a brand being charged against a real ceiling. Measured in prod 2026-08-06, that was the ENTIRE population — 13 funded brand-level ceilings, zero per-funnel rows, and every one of the 13 declaring exactly one active funnel in brand-service. `scripts/attribute-single-funnel-budget.ts` sweeps them (dry-run by default, `--apply` to write); `src/lib/single-funnel-attribution.ts` owns the decision and the write. It is an ATTRIBUTION, not a budget change: the ceiling is the scalar VERBATIM, `updated_at` is COPIED rather than re-stamped (so the brand-level read is byte-identical, timestamp included, and the copied timestamp is the marker of what the sweep touched), and NO `brand_daily_budget_changes` row is written — that table is the timeline of changes to the brand-level number, and this changes nothing about it. The per-funnel product MINIMUM is deliberately NOT enforced: it polices what a customer may newly STATE, and several live ceilings sit below their funnel's minimum ($15, $10, $8, $1 on funnels whose minimum is $24). Every ambiguous case is left exactly as it is — several funnels, no declared funnel, a 0 ceiling, or any brand already carrying a ceiling a human set. Reverse of one row (the scalar is fully recoverable from the ceiling it became) is documented on `attributeBrandBudgetToSingleFunnel`.

  **⚠️ A row copied VERBATIM must be copied inside Postgres — `INSERT … SELECT`, never read-into-JS-and-re-insert.** A `timestamptz` holds MICROseconds and a JS `Date` holds milliseconds, so a value that round-trips through Drizzle is silently truncated: one live row went from `…:32.764549+00` to `…:32.764+00` on the first apply of this sweep (repaired, and `single-funnel-attribution.ts` now does the copy in SQL, pinned by a test). Nothing about money depended on it — every ceiling was identical to the cent — but the truncation is invisible on the 12 rows that were already millisecond-precise, so it only shows if you diff the timestamp of EVERY affected row against a baseline captured beforehand. Same family as the `numeric(16,10)` cents rule: this repo does not put a stored value through a lossier in-memory type on its way back to the DB.

  **brand-service EMITS canonical funnel keys (`sales_meetings_from_conversation`, `sales_meetings_from_website`, `website_purchases`, `form_magnet`); billing stores, serves and accepts the pre-retirement ones** (`BRAND_FUNNEL_KEYS`), which is also what the dashboard collapses both spellings onto. **Both spellings are ACCEPTED on WRITE and resolved to the stored one by `toStoredFunnelKey` — the single resolver, used by the write routes AND the attribution sweep.** Reads never emit a canonical key, so no consumer changed. Two reasons it is not cosmetic: (a) the dashboard already READS both ahead of its own catalogue flipping, so the day it writes what it reads, every ceiling write here would 400 — accepting both is what made the rename safe on brand-service's side; (b) the two spellings name ONE funnel while the composite PK treats them as two, so without resolution `form_magnet` and `visit_form` could both be stored for one brand and the brand-level read (the SUM) would silently DOUBLE. Dedup in `parseFunnelBudgetSet` is on the RESOLVED key for that reason. A spelling neither side can name is a 400 quoting all eight; in the sweep it THROWS rather than being skipped, because a silent skip reads exactly like "this brand declared nothing".
- **The two states are mutually exclusive, on purpose.** The first per-funnel write DELETES the superseded brand-level row (same transaction), and `PATCH /v1/brands/:brandId/daily-budget` answers **409** for a funnel-funded brand (`BrandBudgetManagedByFunnelsError`). So a stale scalar can never sit beside the ceilings disagreeing with their sum.
- **0 is an ordinary value** — "not funding that funnel right now", which is how a customer pauses one — **including a set where EVERY funnel is 0** (a brand in pause, not an error). The "at least one funded funnel" rule belongs to the checkout that spends money; enforcing it here would make it impossible to pause everything from settings.
- **A FUNDED ceiling has a product minimum, and it is a property of the funnel AND the ACQUISITION CHANNEL** — refused with a sentence a person can read. The funnel DEFAULTS live in `BRAND_FUNNEL_MIN_DAILY_BUDGET_CENTS` (`$1/day` for `visit_signup` (Website Purchase) and `visit_form` (Form Magnet), `$24/day` for `reply_meeting` / `visit_meeting`); a channel that states a floor of its OWN overrides it in `ACQUISITION_CHANNEL_MIN_DAILY_BUDGET_CENTS`. Neither is a DB CHECK: the minimums are product figures that move, and a frozen constraint would reject a re-priced offer.

  **`google-ads` is the one channel stating its own floor today: $5/day, on all three visit-led funnels it sells.** A cold-email funnel and a paid-ads funnel do not become viable at the same daily number — one buys sending capacity, the other buys auction placement — so keying the floor on the funnel alone was wrong the moment a second kind of channel arrived. Two of those funnels rise from $1/day to $5 and `visit_meeting` DROPS from $24/day to $5 **on that channel only**. No other channel's floor moved.

  **Which ceilings are judged TOGETHER is `minimumGroupOf`.** A channel with its own floor is judged ALONE on the sum of the offers funding it; every channel stating none is judged with its funnel siblings against the funnel's floor, exactly as before Google Ads. **The two groups never pool** — a dollar of Google Ads cannot lift a sub-minimum cold-email funnel over its floor, and $24 of cold email cannot excuse $1 of Google Ads from its own. That is what keeps "add a cheap channel" from becoming a way to fund anything below the floor it was just refused at, and it is why the pre-existing `$12 + $12 on a $24/day funnel` split is still accepted unchanged.

  **A channel this service prices no floor for is a 400, never a silent fall back to the funnel's floor** (`UnknownAcquisitionChannelError`, refused at parse time and again inside the write, at ANY amount including 0). A channel whose economics differ would otherwise be funded at a number nobody chose for it. The cost is real and accepted: a channel features-service publishes before billing prices it cannot be funded until an entry lands in that table. This is deliberately NOT a second copy of the taxonomy — billing still never asks whether a feature may be SOLD through a funnel; what each entry states is billing's own business, the money a campaign on that channel needs to run.

  **The minimum governs what a customer may NEWLY STATE, not what one has already been running.** The attribution sweep deliberately carried sub-minimum ceilings over verbatim, so live brands are funded below their funnel's floor today (prod: a brand at $8/day on a $24/day reply-to-meeting funnel). Refusing every write of such a ceiling left its owner only two moves — leave it alone, or defund it to zero — and blocked the one direction that helps, raising it TOWARDS the floor. So a funnel whose **stored** ceiling is above zero and below its minimum is grandfathered: re-stating it, raising it to any higher value (still-sub-minimum included), and zeroing it all succeed; **lowering** it to another funded sub-minimum value is refused, because that IS a new statement below the floor. The grandfather is **spent** the moment the ceiling reaches the minimum — that falls out of the ordinary check rather than needing its own branch, since a stored value at or above the minimum never enters the clause. Its refusal message names what the customer can do (keep it, raise it, zero it), not only a minimum they are not allowed to reach downward.

  It is derived from the **stored ceiling and nothing else** — no flag, no column, no per-org override, no backfill, and the minimums themselves are untouched. The grandfather reads that group's own STORED TOTAL, so it behaves for a Google Ads ceiling exactly as it does for a cold-email funnel. Because it needs that stored value, the check moved OUT of `parseFunnelBudgetSet` (which still owns spelling / dedup / non-negative parsing / the unknown-channel refusal before the transaction opens) and INTO `setBrandFunnelDailyBudgets`, where each GROUP is judged against its own rows read under the same `FOR UPDATE` lock. A refusal throws before any write and rolls the transaction back, so a rejected set still leaves nothing half-applied — and per-group judging is what stops one grandfathered funnel in a whole-set write from licensing a sub-minimum value elsewhere.
- **Two write moments, both atomic.** `PUT /v1/brands/:brandId/funnel-budgets` writes the whole set (signup checkout) — funnels absent from the body are removed; `PATCH /v1/brands/:brandId/funnel-budgets/:funnelKey` writes one (brand Settings) and leaves the rest alone. The whole set is validated (`parseFunnelBudgetSet`) BEFORE the transaction opens, so a rejected set leaves nothing half-applied.
- **The history + staff notification carry the brand-level TOTAL, never a per-funnel figure.** Both surfaces describe the number the rest of the fleet reads; showing staff a per-funnel delta beside a total nobody serves is the incoherent-secondary-surface bug. One `brand_daily_budget_changes` row per per-funnel write, in the same transaction.
- Teardown deletes this org's funnel rows (`brandFunnelDailyBudgets` in the internal cascade, counted in `deletedRows`).

**Follow-ups (other repos):** api-service gateway proxy for the two user writes + the user read; brand-service funnel rows stay money-free (the ceiling deliberately lives here, where every money consumer already reads); dashboard Settings + signup checkout UI.

### One ceiling per (funnel, ACQUISITION CHANNEL) — the channel IS a feature slug (migration 0036)

The same sales funnel is now worked through TWO offers at once (a straight sales pitch and a feedback-request pitch). Each (funnel, feature) pair runs its OWN campaign and is measured on its own, so it must be paced and priced on its OWN money: "Sales Meeting from Conversation, straight pitch, $30/day" beside "…, feedback request, $20/day". `brand_funnel_daily_budgets` therefore keys on `(org_id, brand_id, funnel_key, feature_slug)`.

**A channel IS a features-service feature slug.** There is no separate "channel" table, enum or vocabulary anywhere in the fleet, and none was introduced. **Which feature may be sold through which funnel is features-service's statement** — billing stores whatever slug the customer funds and deliberately does NOT validate the pair against a list.

- **Three grains, all SERVED, none re-composed by a consumer.** `getBrandDailyBudget` (brand-wide) is the sum of every pair; the per-FUNNEL figure is the sum of that funnel's pairs (`aggregateFunnelTotals`, the ONE place that sum is built); the pairs themselves are the stored grain. A consumer that sums is a consumer that will disagree with this service one day. For a brand that has never split anything, both derived figures are byte-identical to what shipped before 0036 — the launch gate, runway warnings, credit alerts, the Overview tile and campaign-service's propagation all changed nothing.
- **The reads stayed ADDITIVE.** Both funnel-budget reads (and every write response) keep `funnels: [{funnelKey, dailyBudgetCents, updatedAt}]` unchanged and ADD `channels: [{funnelKey, featureSlug, dailyBudgetCents, updatedAt}]`. The dashboard and campaign-service move onto the finer grain on their own schedule.
- **A slug-less write still works, and cannot silently open a second channel.** `featureSlug` is OPTIONAL on `PUT`/`PATCH` (every caller before 0036 speaks per funnel only). Omitted, it resolves to the funnel's SINGLE channel when it funds one, to `DEFAULT_ACQUISITION_CHANNEL_FEATURE_SLUG` (`sales-cold-email-outreach`) when it funds none, and is refused **409** when the funnel is SPLIT — guessing which of two campaigns the money is for would move it onto the wrong offer. Same shape of refusal as the brand-grain 409 against a funnel-funded brand: the figure the caller addressed is derived one level down.
- **The minimum, and its grandfather, bind a GROUP TOTAL — never one ceiling in isolation.** $12 + $12 on a $24/day funnel is accepted, because the split changes nothing about what the funnel spends per day; the group is the funnel for every channel stating no floor of its own, and the channel alone for one that does (see `minimumGroupOf`). The grandfather is read off the STORED TOTAL of that group, so anything already at or above its floor never enters the clause whatever the split looks like. Judged inside the write transaction on the PROJECTED rows (`projectFunnelRows`), so the outcome is what is tested, not one entry in isolation.
- **`PUT` replaces the whole set at the PAIR grain** — a channel absent from the body is removed even when its funnel is present. 0 stays legal at every grain, all-zero included.

**The migration named the channel each brand actually runs.** Two sales features exist in prod (`sales-cold-email-outreach`, `sales-crm-email-outreach`), so a blanket assignment would have been wrong. Every live ceiling was matched against campaign-service's own campaigns (`org_id, brand_id, funnel_key -> feature_slug`) before the migration was written: of 19 ceilings, 17 resolved to a real campaign (16 cold, **1 CRM** — org `b645207b-…` / brand `ccc29ba2-…` / `visit_signup`, named explicitly in the SQL) and 2 have never had a campaign of any kind, so they took the default. Verified on a full copy of the prod database: 19/19 rows keep their exact amount AND timestamp, brand totals identical (10400 before and after), 18 cold / 1 CRM, PK now 4 columns. **Reversible** — the reverse SQL is in the migration header and was replayed on the same copy, returning the identical 19 pre-migration rows.

`tests/integration/funnel-channel-migration.test.ts` replays the migration file itself against the pre-0036 shape (including a re-apply, which must not re-stamp the CRM row).

### One ceiling per (funnel, channel, OFFER) - the ceiling addresses one campaign (migration 0037)

A new granularity sits between Brand and Campaign: an **OFFER**, one distinct thing a brand sells. brand-service owns the entity and exposes it as a UUID; billing defines none of its semantics and never validates the id against it, exactly as it never validates a channel slug against features-service. A campaign is now **(offer x sales funnel x acquisition channel)**, so the (funnel, channel) key 0036 introduced was one campaign then and is not one now: two offers of one brand selling through the same funnel on the same channel collided on ONE ceiling, so funding one silently funded the other and neither could be stopped alone. `brand_funnel_daily_budgets` therefore carries `offer_id` and the STORED grain is one row per campaign.

- **The wire name is `offerId`, on both writes and both reads.** `PUT /v1/brands/:brandId/funnel-budgets` takes it per entry, `PATCH /v1/brands/:brandId/funnel-budgets/:funnelKey` takes it in the body, and every read/write response gains an ADDITIVE `offers: [{funnelKey, featureSlug, offerId, dailyBudgetCents, updatedAt}]`. `funnels` and `channels` keep their exact shape and meaning: **four grains now, all SERVED, none re-composed by a consumer** - brand total, per funnel (`aggregateFunnelTotals`), per (funnel, channel) (`aggregateChannelTotals`, the ONE place that sum is built), and the stored per-offer rows.
- **`offer_id` is NULLABLE and there is NO BACKFILL, so NULL is a permanent first-class value meaning "not scoped to an offer".** It is not a placeholder waiting to be filled: only brand-service knows which offer a live ceiling belongs to, and guessing moves real money onto the wrong campaign - the same reason 0035 refused to split a brand-level scalar across funnels. Every pre-0037 ceiling keeps it, and behaves precisely as it did.
- **The key is a `UNIQUE ... NULLS NOT DISTINCT` constraint, not a primary key**, because a primary key cannot hold a nullable column. NULLS-NOT-DISTINCT keeps "two unscoped ceilings for one (funnel, channel) pair" unrepresentable, exactly as the old key did, and `ON CONFLICT` on the five columns infers to it - verified, so the upsert path is unchanged. Postgres 15+; the box runs 17 and CI runs 16.
- **An offer-less write still works, and cannot silently open a second ceiling.** `offerId` is OPTIONAL on both writes (every caller before 0037 speaks per funnel and channel only). Omitted, it resolves to the pair's SINGLE offer when it funds one - which for every live brand is the unscoped one - to `null` when the pair funds none, and is refused **409** when the pair is SPLIT across offers. There is deliberately no default offer the way there is a default channel: an offer id is brand-service's to state. Same refusal shape as the brand-grain and funnel-grain 409s: the figure the caller addressed is derived one level down.
- **Channel resolution now narrows by a STATED offer first** (`resolveEntryFeatureSlug`): a brand running two channels under one funnel, one per offer, has exactly one honest answer for a named offer, and refusing it would be an over-refusal rather than a guess. With no rows for that offer it falls back to the funnel's channels as a whole, so a caller naming no offer follows the pre-0037 path verbatim.
- **The minimum and its grandfather are UNTOUCHED: they bind the FUNNEL TOTAL, never one ceiling.** `funnelTotalOf` already sums every row of a funnel, so offer rows just join the sum; the grandfather is still read off the STORED TOTAL, so a funnel at or above its floor never enters the clause whatever the split underneath looks like, and no new dimension can reset one. `projectFunnelRows` keys on (funnel, channel, offer) so the outcome is what is judged.
- **`PUT` replaces the whole set at the OFFER grain** - a ceiling absent from the body is removed even when its funnel and channel are present. Deleting an UNSCOPED row needs `IS NULL` (`offerMatches`); `= NULL` matches nothing and would silently leave it behind. 0 stays legal at every grain.
- **A set may not state one pair both with and without an offer** (400) - the two entries address overlapping grains, so the set does not say which ceiling the offer-less figure is. Same rule 0036 has one level up for the channel. `offerId` is format-checked as a UUID and lower-cased; an unstated offer stays an ABSENT property on `ParsedFunnelBudget`, which is what distinguishes it from a stored `null`.
- The single-funnel attribution sweep writes UNSCOPED (`offer_id` NULL) for the same reason the ceiling has no default offer.

**A ceiling that NAMES an offer REPLACES the pair's pre-offer unscoped one (migration 0038).** The offer resolution shipped in one direction: a write naming NO offer reads the pair's unscoped ceiling as the money of its only offer and updates it in place. The mirror was missing, so the offer-scoped settings page stored a SECOND row for the same campaign and the per-funnel figure - a SUM - counted the customer's money twice. Prod, 2026-08-20: brand `75d7e3e8-…` was authorized at **$90/day on $50 of funding** (a $40 sales ceiling stored once unscoped and once under its offer, plus $10 on the feedback channel), while its two Settings fields each showed the right amount - the dashboard applies the mirror on READ, which is exactly why the incoherence surfaced there as a wrong TOTAL beside right fields.

`supersededUnscopedRows` is the mirror: an entry naming an offer, on a (funnel, channel) pair whose **SOLE** stored ceiling is the unscoped one, deletes that ceiling in the same transaction. Load-bearing details: it fires only when the unscoped row is the pair's ONLY one (a pair already split across named offers has no unambiguous owner for an unscoped remainder, so nothing is attributed - the same refusal posture `resolveEntryOfferId` takes); the adopted row is excluded from `projectFunnelRows`, or the funnel-total minimum would be judged against money this write is removing ($40 replaced by $40 read as $80); and `PUT` (replace) already produced this outcome, since a ceiling absent from the body goes. **The offer-LESS write is untouched** - every caller predating 0037 behaves exactly as before.

Migration 0038 repaired the one live pair (the only one fleet-wide holding both an unscoped and a scoped ceiling), deleting the superseded unscoped row and nothing else. Verified on a full copy of the prod database: 21 rows → 20, fleet total 14400 → 10400, that brand at **5000 from two rows**, re-apply deletes 0. It is idempotent and its reverse (one INSERT) is in the migration header. It does NOT backfill an offer onto any ceiling - `offer_id IS NULL` stays a permanent first-class value.

`tests/integration/funnel-offer-adoption.test.ts` covers the rule; `funnel-offer-duplicate-repair-migration.test.ts` replays 0038. ⚠️ Three cases in `funnel-offer-budgets.test.ts` had to move with it, because they reached their fixtures THROUGH the old behaviour: the unscoped-beside-scoped state is now unreachable by any write (both rows are seeded directly instead), and the two grandfather cases that "opened an offer beside" a ceiling now open it on a second CHANNEL, since naming an offer on the same channel adopts rather than adds.

`tests/integration/funnel-offer-migration.test.ts` replays the migration file against the 0036 shape (including a re-apply, and that the constraint really is 5 columns and NULLS NOT DISTINCT). ⚠️ **Two existing suites had to move with it and would otherwise read as unrelated breakage:** `tests/integration/brand-funnel-budgets.test.ts` asserts whole response bodies with `toEqual`, so the additive `offers` array has to be added there (0036 did the same for `channels`), and `funnel-channel-migration.test.ts`'s `toCurrentShape()` re-creates the table after its replay - leave it on the 0036 shape and every LATER file in the run dies on a missing `offer_id`, because `tests/setup.ts` is `CREATE TABLE IF NOT EXISTS`.

### One OFFER's daily ceiling, on its own read (`aggregateOfferBudget`)

An offer-scoped screen shows a fraction: that offer's spend today over the ceiling it is paced against. The numerator was fixed to cover every channel the offer is sold through; the denominator had only one shape available here, the brand-wide total — which is about a different thing the moment a brand states a second proposition. It reads correctly today for every live brand only because each names ONE offer, a property of the DATA, not of the design. `GET /{internal,v1}/brands/:brandId/offers/:offerId/daily-budget` answers the offer's own ceiling in **one request**, with its per-funnel and per-(funnel, channel) breakdown, so no caller enumerates channels (it does not own that list) and no caller sums (client-side recomposition is what makes two surfaces disagree).

- **Its OWN answer, not a widening of the brand-wide read.** `getBrandDailyBudget`, both funnel-budget reads and every write response are byte-unaffected: their meaning is what the launch gate, runway warnings, credit alerts, the Overview tile, campaign-service's propagation and this service's own affordability checks pace real spend on. A per-offer array was deliberately NOT folded into the funnel-budget view either — a test pins its absence, so a consumer cannot start reading a fifth grain there by accident.
- **An UNSCOPED ceiling (`offer_id IS NULL`) counts towards an offer only while that offer is the brand's SOLE named one.** Then the brand's money has exactly one campaign-owner, so the offer's total IS the brand total and no live brand's screen moves. With two named offers there is no honest owner for an unscoped remainder and it belongs to NEITHER — the same posture `resolveEntryOfferId` / `supersededUnscopedRows` take one grain down, where an unscoped ceiling is an offer's money only while it is the pair's only one. Nothing is attributed, stored or backfilled by this read; it is a pure read.
- **Nothing stated is not zero.** An offer with no ceiling answers `dailyBudgetCents: null` (and `updatedAt: null`, empty arrays) — never the brand total, never 0, and a ceiling of 0 (funded at nothing) is never rendered as null. A brand funded only at the brand grain names no offer, so every offer of it answers null.
- **No discount, ever.** A ceiling is a CONFIGURATION value, not a charge; the per-org usage modifier applies to cost rows only. There is no "net daily budget" concept at any grain (see "Per-org usage discount").
- Offer ids are lower-cased on read, matching how the write stores them. `aggregateOfferBudget` is the ONE place the per-offer sum is composed, as `aggregateFunnelTotals` / `aggregateChannelTotals` are for theirs.

Verified against the live case (org `b645207b-…`, brand `75d7e3e8-…`, offer `d5ecba00-…`): $50 stated under that offer on `sales-cold-email-outreach` plus $10 left UNSCOPED on `feedback-request-cold-email-outreach` — the offer answers $60, byte-equal to the brand total that brand's screen shows today. Covered by `tests/integration/brand-offer-daily-budget.test.ts`.

### One ceiling per (funnel, channel, offer, LEG) - the ceiling is keyed on what the campaign is bought for (migration 0039)

A campaign has been redefined as **(brand, offer, acquisition channel, LEG)**. A sales funnel is a chain of steps and the thing a customer BUYS is one of its LEGS: the leg that takes a lead sitting at one step and moves it to the next. One leg belongs to SEVERAL funnels at once (a booked meeting becomes an attended meeting in both meeting funnels), so the funnel is leaving a campaign's identity and becoming a way of READING legs rather than the unit anything is keyed on. Ceilings here were the last place the funnel was load-bearing for MONEY, so a campaign and the money pacing it were keyed on two different things. `brand_funnel_daily_budgets` therefore carries `leg_key` and the STORED grain is, again, one row per campaign.

**This is the ADDITIVE half.** The funnel STAYS in the key, every existing read answers exactly what it answered before, nothing became required, and a LATER ship removes the funnel once every consumer has moved. Removing it here would break production.

- **The identifier is features-service's and it is OPAQUE.** It mints the value (`lib/funnel-legs.ts`, published on `GET /public/channels` as `legs[].legKey`) and campaign-service carries the same one on the campaign row (v0.64.0). billing stores whatever the customer funds, validates it no more than it validates a channel slug or an offer id, and NEVER parses it — the two steps a leg connects ride BESIDE the identifier on that catalogue (`fromStep` / `toStep`), so a consumer that wants them reads them there. Splitting the string is how a second, drifting vocabulary starts. `text`, because that is the shape features-service mints; the shape check is "non-empty" and nothing else.
- **Five grains now, all SERVED, none re-composed by a consumer.** `getBrandDailyBudget` (brand-wide) is the sum of every row; per FUNNEL (`aggregateFunnelTotals`); per (funnel, channel) (`aggregateChannelTotals`); per (funnel, channel, offer) (`aggregateOfferTotals`, the ONE place that sum is built); and the stored per-leg rows. For a brand that has never stated a leg, all four derived figures are byte-identical to what shipped before 0039 — the launch gate, runway warnings, credit alerts, the Overview tile and campaign-service's propagation changed nothing.
- **The reads stayed ADDITIVE.** Both funnel-budget reads, the offer read and every write response keep `funnels` / `channels` / `offers` unchanged in shape and meaning, and ADD `legs: [{funnelKey, featureSlug, offerId, legKey, dailyBudgetCents, updatedAt}]`. `offers` is now a SUM rather than the stored grain, which for every live brand is the same number on the same rows.
- **PRECEDENCE, stated once: a leg-keyed ceiling REPLACES the leg-less one describing the same money.** They are never summed and never both stored. `supersededLegLessRows` is the mirror of `resolveEntryLegKey`, exactly as `supersededUnscopedRows` mirrors `resolveEntryOfferId` one grain up: an entry naming a leg, on a (funnel, channel, offer) triple whose SOLE stored ceiling is the leg-less one, deletes that ceiling in the same transaction, because the customer is RE-STATING the one ceiling that triple was funded at and every figure above it is a SUM. ONLY when the leg-less row is the triple's sole one — a triple already split across named legs has no unambiguous owner for a leg-less remainder, so nothing is attributed. The adopted row is excluded from `projectFunnelRows`, or the minimum would be judged against money the write is removing.
- **A leg-less write still works, and cannot silently open a second ceiling.** `legKey` is OPTIONAL on `PUT`/`PATCH` (every caller before 0039 speaks per funnel, channel and offer only). Omitted, it resolves to the triple's SINGLE leg when it funds one — which for every live brand is the leg-less one — to `null` when it funds none, and is refused **409** when the triple is SPLIT across legs. There is deliberately no default leg the way there is a default channel: a funnel has several legs and a leg belongs to several funnels, so nothing here can pick one. Same refusal shape as the brand-, funnel- and offer-grain 409s.
- **The per-funnel product MINIMUMS are untouched and keep binding the GROUP TOTAL, never one ceiling.** `funnelTotalOf` already sums every row of a funnel, so leg rows just join the sum; the grandfather is still read off that group's STORED TOTAL, so a funnel at or above its floor never enters the clause whatever the split underneath looks like, and no new dimension can reset one. $12 + $12 across two legs of a $24/day funnel is accepted, exactly as it is across two channels.
- **`PUT` replaces the whole set at the LEG grain** — a ceiling absent from the body is removed even when its funnel, channel and offer are present. Deleting a leg-less row needs `IS NULL` (`legMatches`); `= NULL` matches nothing and would silently leave it behind. 0 stays legal at every grain, all-zero included.
- **A set may not state one triple both with and without a leg** (400) — the two entries address overlapping grains, so the set does not say which ceiling the leg-less figure is. Same rule 0036 and 0037 have one and two levels up.
- The single-funnel attribution sweep writes LEG-LESS (`leg_key` NULL) for the same reason it writes unscoped by offer.

**`GET /{internal,v1}/brands/:brandId/legs/:legKey/daily-budget`** answers ONE leg's ceiling — the money that paces one campaign, read on the same key the campaign itself is keyed on — as the SUM of the ceilings funding it across every funnel, channel and offer it is sold through, plus that leg's own per-funnel / per-channel / per-offer breakdown and its stored rows. It is its OWN answer, not a widening of any existing read. A LEG-LESS ceiling counts towards a leg only while that leg is the brand's SOLE named one (the same rule `offerBudgetRows` holds one grain up, so no live brand's screen moves); with two named legs the remainder belongs to neither. Nothing stated is not zero: a leg with no ceiling answers `dailyBudgetCents: null`, never 0 and never the brand total. No discount, ever — a ceiling is a configuration value.

**NO BACKFILL, and `leg_key IS NULL` is a permanent first-class value** meaning "not scoped to a leg", not a placeholder. Only the customer knows which leg a live ceiling is for, and guessing would move real money onto the wrong campaign — the same refusal 0035 made about splitting a brand scalar and 0037 about attributing an offer. Verified on a full copy of the production database: **21/21 rows keep their exact amount, timestamp, channel and offer** (0 rows changed), the fleet total stays **26400**, the key becomes 6 columns `NULLS NOT DISTINCT`, and a re-apply touches nothing. **Reversible** — the reverse SQL is in the migration header.

`tests/integration/funnel-leg-budgets.test.ts` covers the rule; `funnel-leg-migration.test.ts` replays 0039 against the 0037 shape (including a re-apply and the constraint's shape). ⚠️ As with 0036 and 0037, `tests/setup.ts` is `CREATE TABLE IF NOT EXISTS`, so a local DB that has run the suite before needs `DROP TABLE brand_funnel_daily_budgets` once; and both earlier migration tests' `toCurrentShape()` had to move to the 0039 shape, or every LATER file in the run dies on a missing `leg_key`.

## Campaign affordability gate (read-only pre-flight)

Stops a credit "retry storm": an out-of-credit org's recurring campaign was re-triggered every minute by campaign-service, each run doing paid Apollo enrichment then 402-ing at the LLM step. campaign-service now asks billing "can this org afford another run of campaign X?" BEFORE dispatching — billing answers live, per-campaign, **without charging or reloading**.

**Cost estimate (no up-front truth).** The run's cost isn't known before the run. We use the `required_cents` of the **LAST authorize attempt for that campaign** as the estimate — a campaign re-runs the same workflow, so cost is ~constant. The estimate is upserted in `POST /v1/customer_balance/authorize`: when `x-campaign-id` is present, `upsertCampaignAuthorizeCost(campaignId, orgId, requiredCents)` runs right after `requiredCents` resolves, on **both sufficient and insufficient** outcomes (it's the cost of the last attempted run). Absent `x-campaign-id` (dashboard chats) → skipped; never fails the authorize. Fail-loud on a write error. Does NOT touch the reload / depletion / response-shape flow.

**State:** one table, `campaign_authorize_costs` (migration `0021`, hand-journaled) — `campaign_id` PK, `org_id`, `last_authorize_required_cents numeric(16,10)`, `updated_at`. One row per campaign, upserted in place (`ON CONFLICT (campaign_id) DO UPDATE`). `src/lib/campaign-costs.ts` owns the upsert + read.

**`GET /internal/campaigns/:campaignId/affordability`** (`src/routes/internal.ts`, service-auth, READ-ONLY — no charge, no reload, no episode mutation):
- No stored cost → `{affordable:true, balanceCents:"0", lastRequiredCents:null, hasHistory:false}` (first-run default — a brand-new campaign runs once to establish its cost; the org isn't resolvable without a stored row, hence `balanceCents:"0"`).
- Stored cost → live balance via `computeBalance(stored.orgId)` (user-less balance path — X-API-Key + org only, NO `x-user-id`/sentinel, see stripe-service integration shape); `affordable = balanceCents >= lastRequiredCents`, `hasHistory:true`. Fail-loud 502 if stripe/runs unreachable. 400 on non-UUID `campaignId`.

## Boot-time email template registration (`src/instrument.ts`)

transactional-email-service resolves a template by looking up the row whose `name` equals the `eventType` of the send. An unregistered template therefore makes **every** send of that event throw "No template for event" — the email silently never arrives, and nothing on the sending side notices (all our sends are fire-and-forget by design).

**`src/instrument.ts` was dead code from the day it was written.** It ran its `PUT /templates` upsert as a top-level side effect in a module imported by NOTHING: no import in `src/index.ts`, no `--import`/`-r` preload in `package.json`, and the container command is a plain `node dist/index.js` (Dockerfile `CMD`). Measured consequence in the prod template store: **36 templates, zero of them billing's** — so `credits-reload-failed` had been failing on every fire since it shipped, and `brand_daily_budget_changed` (v0.57.0) was live, tested and mute. It is now an exported `deployEmailTemplates()` called from `src/index.ts`.

- **Called from inside the `app.listen()` callback, `void`-ed, never awaited.** The port is bound before the call even starts, so an email service that is slow, mid-deploy, restarting or erroring cannot delay or fail the boot. (The original hazard was named as a cold Neon compute waking from scale-to-zero; Neon is gone and nothing suspends, but a sibling service is still reachable-or-not on its own schedule, and a boot that waits on one is a boot that can fail for a reason unrelated to itself.) `deployEmailTemplates` never throws (own `try/catch`) and never rejects; it returns a boolean and logs loudly on failure. Bounded by `AbortSignal.timeout(15s)` and wrapped in the shared `fetchWithRetry` (the upsert is idempotent, so a connect-phase retry is safe). A boot that cannot reach the email service still serves traffic — templates land on the next restart.
- **Idempotency is the receiving `PUT /templates` upsert-by-name. No table, no flag, no "already registered" marker** — every restart and every replica re-sending the identical payload is correct by construction.
- **Register a template if and ONLY if some code path here sends its `eventType`.** Today that is exactly two: `credits-reload-failed` (`src/routes/customer_balance.ts`) and `brand_daily_budget_changed` (`src/lib/brand-budget-notification.ts`, whose exported constant is imported into the template row so the two cannot drift). A third, `credits-depleted`, sat here for months with **zero senders** — the dunning engine sends `credit-depleted` (singular) — and was deleted rather than registered.
- **The six dunning templates (`credit-depleted`, its two follow-ups, and their three `-blocked` variants) are NOT ours to register.** The dashboard owns that copy (distribute.you#1420) and all six are present in prod. Do not add them here — two services upserting the same name by boot order would fight over the body.
- **Never paper over a missing template** with an inline body, a default template, or a swallowed send error. The template store is the single source for template content; a send failing loudly in the logs is the correct signal that a registration is missing.
- `tests/unit/instrument-templates.test.ts` guards this. Note the first case reads `src/index.ts` as text and asserts the call site exists AFTER `app.listen(` and is not awaited — a behavioural test cannot see "nobody imports this module", which is the bug that shipped.

## Out-of-credit dunning engine (issue #147)

Emails a customer whose recurring campaign stopped because credit hit zero — instant, then +3d and +10d while still depleted; stops the moment they recharge. billing-service owns it because it knows both the balance and the auto-topup/reload lifecycle. The dashboard banner/modal (distribute.you#1418) is the in-app half; this is the email half. Email **copy** is owned by the dashboard (templates registered in `instrumentation.ts`, distribute.you#1420) — billing only triggers by `eventType`.

**State:** one table, `credit_depletion_episodes` (migration `0019`, hand-journaled). A **partial unique index `(org_id) WHERE recovered_at IS NULL`** enforces at-most-one OPEN episode per org — this is the idempotency + re-arm mechanism (a fresh depletion only opens after the prior episode recovered). Per-stage `t0_sent_at` / `followup_3d_sent_at` / `followup_10d_sent_at` give at-most-once-per-stage. `credited_cents_at_open` (migration `0020`, `numeric(16,10)`, nullable) records the `credited` snapshot at depletion — the recovery baseline (see Scheduler).

**Detect (T0):** in `customer_balance/authorize`, every `sufficient:false` return calls `openDepletionEpisodeIfDepleted` (`src/lib/dunning.ts`). It self-gates: opens only when `isDepleted(balance)` (balance ≤ 0) AND the request carries **campaign activity** (`x-campaign-id` OR `x-workflow-slug` OR `x-feature-slug`). Open = INSERT relying on the partial-unique index; a `23505` unique violation means "already open" → no-op (T0 not re-sent). Other errors fail loud. On a fresh open it fires the `credit-depleted` email. (Replaced the old un-idempotent inline `credits-depleted` sends; the legacy `credits-reload-failed` send is unchanged.)

**Scheduler (`src/lib/dunning-scheduler.ts`):** in-process self-rescheduling `setTimeout` loop started after `migrate()`, before `app.listen()` (mirrors campaign-service). Hourly. `runDunningTick` scans open episodes, recomputes balance via `src/lib/balance.ts` (shared with the route), and per episode: **real recharge** (`credited` rose above `credited_cents_at_open`) → set `recovered_at`, no email (stop-on-recharge); still depleted → send due `+3d`/`+10d` via **atomic claim** (`UPDATE … WHERE <stage> IS NULL RETURNING`) so overlapping ticks / multiple replicas never double-send. A per-episode balance-recompute failure is logged and skipped (retried next tick) — never blocks other orgs.

**Recovery is keyed on `credited` rising, NOT on `balance > 0` (migration 0020, v0.30.1, GH #170).** `usage` (runs-service `spent_cents`) includes **provisioned holds**, so `balance = credited − usage` flutters around zero as holds reserve/release on an org running campaigns at ~0 balance. The pre-0020 code closed the episode on any `balance > 0` tick, then the next depleted authorize re-armed a fresh episode + fired a **new T0 email** — customers got duplicate "out of credit" emails (3 orgs, up to 5× each). `credited` (paid topups + promos) only ever *rises*, so it never flutters: a recharge is the only thing that closes an episode. Follow-ups still gate on `isDepleted(balance)` at tick time (a transient positive balance sends nothing, leaves the episode open). Rows opened before `0020` (null baseline) are lazily backfilled on the next tick (`credited_cents_at_open = creditedNow`, no recovery that tick). **Never revert recovery to a `balance`-based check** — that reintroduces the duplicate-email bug.

**Recipient:** `recipientEmail` = the Stripe customer billing email (`customer.email`, on the wire from stripe-service `GET /v1/customers`); when null the email-service resolves via `x-user-id`. eventTypes are **byte-equal** to the dashboard templates (`DUNNING_EVENT_*` in `schema.ts`): `credit-depleted`, `credit-depleted-followup-3d`, `credit-depleted-followup-10d` — these are NOT in transactional-email-service's dedup sets, so dedup is entirely billing-side. No new env vars (reuses `TRANSACTIONAL_EMAIL_SERVICE_*`, `STRIPE_SERVICE_*`, `RUNS_SERVICE_*`).

**Blocked-card variant routing (4th out-of-credit surface, issue #220).** When the org's saved card can't be charged off_session (auto-reload-blocked country, e.g. India / RBI — `snapshot.autoReloadSupported === false` from `computeBalance`), the base templates' "turn on auto-topup" nudge is a dead-end. So each stage routes to a `-blocked` sibling eventType (`DUNNING_EVENT_*_BLOCKED` in `schema.ts`): `credit-depleted-blocked`, `credit-depleted-followup-3d-blocked`, `credit-depleted-followup-10d-blocked`, whose copy nudges a manual recharge. The `-blocked` template rows already exist in the transactional-email prod DB (byte-equal to the originals bar the auto-topup sentence). `src/lib/dunning.ts:dunningEventType(base, autoReloadSupported)` is the only selector — pure string routing, copy stays in the DB. T0 reads `autoReloadSupported` threaded through `OpenEpisodeParams` from the authorize-route snapshot; the +3d/+10d ticks read `snapshot.autoReloadSupported` directly (no extra Stripe call). The 3 in-app surfaces (billing-guard modal, runway banner, onboarding reminder) were fixed in distribute.you#2240.
